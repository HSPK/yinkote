# 16 · 工作区规则（Workspace Rules）

> 这份文档描述的是**已经实现并有测试守护**的规则，不是愿望。
> 修改工作区行为前先读它；改完之后**回来更新它**。
> 每条规则对应 `web/src/tabs.render.test.tsx` 里的一个测试。

---

## 1. 没有二级弹窗

**任何"你在里面工作"的界面都是 tab，没有例外——包括设置。**

弹窗表达不了文献工作的形态：读 PDF、做标注、就它提问、翻库，这些是**并行**发生
的，常常持续一小时。弹窗会抢走整个屏幕、堆叠起来很糟、关掉就丢状态。

允许存在的浮层只有三类，它们都**不是界面，而是一次交互**：

| 浮层 | 为什么不是 tab |
| --- | --- |
| 命令面板 | 打开就是为了立刻关掉 |
| 确认框 / 输入一个字符串 | 一次性回答，无状态可言 |
| toast、右键菜单、下拉 | 瞬时反馈 |

判据很简单：**关掉它会不会丢掉你正在做的事？** 会，就必须是 tab。

已按此规则搬迁的界面：设置、插件、状态、收藏夹编辑器、Zotero 导入、
图谱、必读缺口、阅读器、对话。

## 2. Tab 模型

### 2.1 一件事一个 tab

id 就是 `kind:target`（无 target 的界面 id 就是 kind）。**再次打开同一件事是聚焦，
不是新开。**

### 2.2 预览槽位（斜体）只有一个，且跨类型共享

斜体 = 这是一次**瞥一眼**。翻十篇论文不该留下十个 tab，所以下一次瞥一眼会
**顶掉**上一个，并且**保持它原来的位置**（否则 tab 条会在鼠标底下乱跳）。

关键点：这个槽位是**全局唯一**的，不是每种类型各有一个。否则每种类型都会各漏一个。

### 2.3 什么以预览打开，什么直接固定

| 打开方式 | 结果 |
| --- | --- |
| 单击列表里的论文 / 图谱节点 / 历史对话 | **预览**（斜体） |
| 新建对话、新建收藏夹 | **固定**——"新建"本身就是意图 |
| 设置、插件、状态、必读缺口、收藏夹浏览 | **固定**（它们是目的地，不是一瞥） |

### 2.4 什么会把预览变成固定

- 双击 tab 标题；
- **在里面写了字**——发出一条对话消息、做一个高亮。
  在一个界面里输入，是"这不是随便看看"的最强声明。

反向永远不会发生：**固定的 tab 不会退回预览。**

### 2.5 切换 tab 不改变任何 tab 的预览状态

从 chat 切到 library 再切回来，chat 还是原来的样子。切换只是切换。

### 2.6 每个 tab 记住自己在看什么

library 类型的 tab 各自拥有一份 scope（当前集合、选中项、滚动位置、搜索词）。
切走时保存、切回时恢复。**关闭时丢弃**——否则每开过一次 tab 就泄漏一份条目列表。

### 2.7 关闭之后去哪

右邻，没有右邻就左邻，都没有就回 library。这是所有编辑器的做法，肌肉记忆认它。

library tab 永久存在，关不掉。

## 3. 曾经踩过的坑（不要重犯）

### 3.1 对话 tab 从不使用预览槽位

用户报告"tab 跳转逻辑很混乱"，根因就在这里：`openConversation` 打开的是固定 tab，
于是**翻看三个历史对话就留下三个 tab**，而翻看三篇论文只留下一个。同一个手势
（在列表里点一下）在两个地方含义不同——混乱正是这么来的。

**教训：一个手势在整个应用里只能有一个含义。** 现在 13 条规则每条都有测试。

### 3.2 只测纯函数，测不出这类问题

`lib/tabs.ts` 的单元测试一直是绿的，因为纯函数从来没错。错的是**界面向它请求了什么**。
这类 bug 只有把整个工作台渲染出来、真的点下去才会现形——和当初拖放、图谱点击
是同一形状。

**教训：涉及交互的改动，测试写在 `*.render.test.tsx` 里。**

### 3.3 Agent 有写权限，就必须有审计痕迹

Agent 现在可以**增删改查**整个库（17 个工具，其中 12 个会写）。这带来一条硬规则：

**每一次工具调用都画在它发生的位置**，夹在促成它的那句话和随后那句话之间，
而不是在回答末尾折叠成一份摘要。

理由不是好看。摘要丢掉的恰恰是让回答**可核查**的东西：**哪一步导致了哪一步**。
一个由你看不见的检索拼出来的答案，你没有办法验证它；而一个改动了你的库的动作，
你必须能追溯到究竟是哪句话让它发生的。

配套的三条：

- **写操作有标记**（accent 色边 + 徽标）。"这些里面哪些真的动了东西"是任何人
  看到 trace 的第一个问题。
- **参数直接可见，返回值折叠**。参数很短，且正是"到底问了什么"；返回值常是一整页 JSON。
- **默认可逆**：`trash_items` 是推荐路径，永久删除是**另一个**工具，
  描述里直说"不可撤销"，并且提示词要求除非用户明确要求，否则一律用回收站。

`/api/v1/agent` 会列出全部工具与其中的写工具，所以"它能改我的库吗"不用读源码就能回答。

### 3.4 长任务属于它的对象，不属于发起它的请求

一次 agent 回合可能跑半分钟。把它绑在一个 HTTP 请求上，意味着**切个 tab、刷新一下
就把模型已经在做的工作丢掉了**——模型无论如何都会算完，唯一的问题是还有没有人
在那里接住答案。

所以：`ask` 立刻返回；进度走事件总线（和其它所有变更同一条）；`GET …/run` 随时可读，
这正是新打开的页面能**重新接上**一个进行中回合的原因。

配套设计：

- **推整份状态，不推增量。** 状态很小（几个步骤加一行文字），而错过一个增量的客户端
  会永久性地不同步，并且**自己无从察觉**。
- **中断是循环在步骤之间检查的标志位，不是丢弃 future。** 已经发出的请求无论如何都会
  返回，扔掉它的答案只意味着以后要再付一次钱。
- **一个对话同时只能有一个回合**——第二个直接拒绝而不是排队。两个回合的工具调用会
  交织成没人读得懂的记录。
- **步骤从 run 持久化，不从 transcript 重建。** 于是"实时看到的回合"和"明天读回来的
  回合"是同一个东西，而不是两种可能漂移的渲染。

### 3.5 步骤显示：标题不动，内容向下长

一个步骤是**一行固定高度的标题栏**（工具名 + 参数 + 展开箭头），展开时内容长在
**它下面**。标题不动，因此上方的一切都不会移位——这是"读一份记录"和"追着记录
在屏幕上跑"的区别。这也是它不用 `<details>` 的原因：`summary` 是文档流的一部分。

- 步骤与回复**同一条左边界**，于是一个回合读起来是一列：思考、动作、思考、回答；
- **参数放在标题行**（很短，且正是"到底做了什么"），**返回值折叠**（常是一整页 JSON）；
- **模型的 reasoning 默认折叠**，且单独一类。它是**过程不是答案**，
  当作正文展示等于把草稿当结论。

### 3.6 和模型说话的代码只放一处（`yk-ai`）

参考 `pi-ai` 的分法：**provider 契约、消息类型、流式事件、各家方言**全部收进一个 crate。

在此之前它们散在三处：类型在 `yk-core`、chat 方言在 `yk-server`、embedding 方言在
`yk-search`。三个地方必须彼此吻合，而其中任何一个都**没法单独测试**——测 chat 方言
要拖起一个 HTTP 服务，测 embedding 要拖起一个数据库。

现在的分层：

```
yk-ai/
  types.rs           消息、工具、请求（每家 provider 共用一套）
  stream.rs          Delta：Text / Reasoning —— 各家差异到此为止
  provider.rs        ChatProvider / EmbeddingProvider 契约
  providers/openai.rs  OpenAI 方言（chat + SSE），也就是 Ollama/vLLM/LM Studio 说的话
  providers/embeddings.rs  本地哈希 + OpenAI 兼容
```

`yk-ai` 只从项目其余部分借一个 Error 类型，其它一无所知——它不知道文献库、条目或 SQLite。

**流式是主方法，不是可选项。** `complete(request, sink)` 是唯一的实现点，
`answer(request)` 是"我不要碎片"的便捷包装。这样 provider 必须**主动放弃**流式，
而不是**忘记**支持它。

### 3.7 "流式坏了"之前，先确认服务端是不是在缓冲

实测教训：开发用的这个端点发出的 SSE **格式完全正确**，199 个事件——但首个事件在
请求后 **7.46 秒**才到，且 199 个全部在 **0.05 秒内**涌完。它算完整个答案，然后
假装流式发出来。

这一侧没有任何东西可修。**唯一能分辨的办法是给到达时间打点，而不是读报文格式。**

### 3.8 慢、会失败、值得重试 ⇒ 它是队列，不是请求

下载文件同时具备这三条性质，所以它是**队列**：点击立刻返回、凌晨三点超时的出版商
早上还能重试、两者都不依赖浏览器标签页还开着。

队列存在**数据库**里：进程一重启就忘光的队列不是队列，是缓冲区。

三条已被测试钉住的判断：

- **同一个文件问两次是一次请求**（双击按钮是最常见来路）；
  但对**已失败**的行再问一次意味着"再试一次"——那是人再按一下的意思。
- **失败原因留在行边上，不写日志。** 它是"要不要重试"这个决定的依据，
  而日志是没人会去看的地方。
- **重试清除原因、保留尝试次数。** "已经失败四次"值得知道，而清空恰恰会掩盖它。

队列是**界面**不是 toast：下载不是一个事件——它需要的决定发生在它出错之后。

### 3.9 会改动一批文件的操作，必须先能预览

批量重命名的渲染是**纯函数**，因此可以在动手前精确展示结果。
**无法预览的批量操作不该被运行**，冒烟里有一条断言"预览不改变任何东西"。

文件名相关、不写测试就会咬人的细节：

| 细节 | 为什么 |
| --- | --- |
| 缺作者时折叠间隔 | ` 2017 - Title` 看起来像程序出错 |
| 取三平台最严的字符规则 | 在 Linux 合法、Windows 非法的名字，会把同步目录变成一串错误 |
| 去掉结尾的点 | Windows **静默**去掉它，文件就不在数据库说的位置了 |
| 标题里的换行 | 出版商放进去的频率远超想象 |
| 按**字符**截断 | 真实库里一半标题不是 ASCII，按字节切会 panic |
| 未知占位符渲染为空 | `{авторы} 2017.pdf` 读起来像文件损坏 |

**先移动字节，再更新记录。** 反过来会让库指向一个不存在的文件；
这个顺序留下的是"名字过期但仍能找到"的文件。

### 3.10 跨边界的响应一律 camelCase，并且有测试强制

`Missing` 曾以 `cited_by` 发出，而前端读 `citedBy`——**那一列从发布第一天起就是空的**，
而计数正是那个视图存在的全部意义。没有任何东西失败。

**为什么没被发现**：渲染测试的 fixture 是照着**前端自己的类型**写的，于是它和前端就
一份双方都没验证过的契约达成了一致。**照着自己要喂的类型抄出来的 fixture，
对契约什么也没测到。**

两道防线：

1. `crates/yk-server/tests/wire_names.rs`——序列化每一个跨边界类型，
   断言没有键包含 `_`。**没人能强制的约定，就是会被再次破坏的约定。**
   （加进去之后我特意去掉一次属性，确认它确实会失败。）
2. 冒烟套件对的是**真实服务器**，字段名断言写在那里。

例外只有配置文件（`Config` 等）：TOML 里 snake_case 是对的，改名会毁掉现有配置。

### 3.11 会累积状态的冒烟测试，最终测的是累积本身

图谱的两条冒烟检查开始失败了，而产品完全正确。原因：每轮冒烟都用**同一个标签**
新建两个条目，二十多轮之后这个标签打在了 **54** 个条目上——越过了"这个标签太常见、
不足以说明相关性"的阈值（50），于是规则**正确地**把它排除了。

**教训：对着长期存在的数据库跑的测试，必须自带一次性的标识。**
否则它测的不再是规则，而是历史。

（同一条也解释了为什么冒烟里那些"数量"断言要写成"错误答案为空"的形式，
而不是断言一个具体数字——数字会随累积漂移，而形状不会。）

### 3.12 SQLite 的变量上限是悬崖，不是斜坡

一条语句里每个 key 占一个绑定变量，SQLite 最多绑 32766 个。于是"全选 → 移到回收站"
这个一直好用的动作，会在某个人的文献库长到三万条之后**突然报错**——不是变慢，是直接失败。

这类 bug 的特征：**功能从第一天就写错了，但要等数据长大才会暴露**，所以任何小数据集上的
测试都测不出来。修法是在**调用方已有的事务内**分块（每块 900），这样四万个 key 依然是
一次全有或全无的操作，只是拆成了几十条语句。

已收口的路径：`set_trashed`、`get_many`、共享的 `hydrate`、附件的父条目查询（重命名预览
会一次性拿走全库附件）。剩下两处 `IN` 在拼装好的 predicate 里，属于同一条语句无法拆分，
但都受 `MAX_LIMIT`（500）约束，已在代码里注明"要变大就得分页，而不是把列表拉长"。

测试写法：直接造 40000 条。慢几秒，但这是唯一能证明悬崖被填平的方式。

### 3.13 落地页不是 PDF

用户粘贴的地址十有八九是论文的**介绍页**，不是论文本身。早先的实现会把这段 HTML 原样存
成"PDF"，于是文献库里塞满打不开的文件；换个写法直接报错，用户看到的就是一整列失败记录。

正确做法是业界既成事实：读页面 head 里的 `citation_pdf_url`（Google Scholar 认的那个 meta，
所以几乎所有出版商和仓储都会输出），跟进一次。arXiv 摘要页现在能自动取到 PDF。

**不要**退化成"扫描页面里所有像 .pdf 的链接"——那样会兴高采烈地下载"本期全文合订本"。
找不到就明说找不到，比猜错强。

### 3.14 每个 tab 一律平等，library 也不例外

library tab 曾经是 `permanent: true`，不能关。一个例外就够让**所有**关于 tab 的规则都要
补一句"……library 除外"，而且带来一个真 bug：在 chat 里点左侧的 collection，新 scope 被
写进了当前聚焦的那个 tab，界面上看起来**什么都没发生**。

现在 `navigate()` 会先确保有一个能承载 library 的 tab 并聚焦它，library 和别的 tab 一样能关，
关掉最后一个 tab 会进入一个**说明如何回来**的空状态——而不是靠钉死某个 tab 来回避这个状态。

### 3.15 换掉答案之前，先把新的拿到手

每轮对话结束都会闪一下。原因是顺序写反了：先记录"跑完了"（实时气泡随即卸载），**再**去
网络取存好的那份答案。中间整整一个来回，答案根本不在屏幕上，然后一模一样的内容又出现——
看起来就像"结束后统一刷新了一下"。

规则：**先取，再一次性替换**，两者放在同一次 `set` 里。回归测试把那次 fetch 挂住不返回，
用旧顺序必然失败（已验证）。

### 3.16 Skills：提示词里只放"什么时候用"，不放"怎么做"

技能是磁盘上的文件夹 + `SKILL.md`（frontmatter 写 name / description，正文写步骤）。
系统提示每轮只带**名字和一行描述**，正文要等模型自己调用 `read_skill` 才发过去。

这么做的理由是省下的那部分：把所有可能用到的流程都塞进系统提示，等于每一轮——包括"我库里
有多少篇扩散模型的论文"这种——都要为它付费。

两条约束：
- description 必须写**何时适用**（内置技能有测试强制它以 "Use when" 开头）。写成"本技能包含
  ……"的描述永远不会被选中，因为那是模型唯一能不花代价看到的信息。
- 技能是文件而不是代码，用户能读、能改。已存在的文件**不覆盖**——改过的技能属于改它的人。

顺带：步骤预算从 6 提到 16。一次文献检索是 read_skill → 概览 → 站内检索 → 站外检索 → 若干
次 quick_add，6 步刚好耗尽，产出一个看起来像"答得差"的半成品。

### 3.17 Agent 的文件与命令能力：开关就是边界，别假装有别的

文件读写限制在**一个**目录里。不是因为沙箱能让任意代码变安全（不能），而是"agent 只能碰
这个文件夹"是用户能记住的一句话，"agent 能碰你的主目录，除了……"不是。

路径检查上踩过的坑：`..` 不要试图解析，**直接拒绝**。`Path::parent()` 是纯词法的，它剥掉
`..` 而不是向上走，所以早期版本里 `notes/../../../secrets` 顺利走出了工作区。合法路径都写得出
不带 `..` 的形式。软链接则必须靠解析最深的已存在祖先来挡，字符串检查一定漏。

命令执行默认关闭，靠 `agent.allow_commands` / `YK_AGENT_ALLOW_COMMANDS=true` 打开。
**没有白名单**：`python -c` 就能绕过任何按程序名列的白名单，一个看起来比实际更强的边界
比一个诚实的开关更糟。

### 3.18 @提及：带 key 走，不要让模型再猜一遍标题

输入框里打 `@` 挑一篇论文，附带的是 **item key**，不是文本。理由很实际：用户已经指明了
是哪一篇，让模型拿着半截标题再去搜一次，既多花一步，有时还会搜到另一篇同名的。

被提及的论文以 system message 的形式放在这一轮的最前面（最近 8 篇），并且**存进
`message_mentions` 表**——写入和消息本身在同一个事务里，否则索引会和它所描述的对话不一致，
而这种不一致要等到有人发现某篇论文的历史里少了一条才会暴露。

反向查询（"这篇论文我都问过什么"）用 `EXISTS` 而不是 join：一场对话里提到同一篇九次，
它仍然是一场对话，事后去重是白做的功。

对话还可以绑定到某个 collection（复用 `conversations.scope` 列），同时给 `search_library`
加了真正的 `collection` 参数（递归包含子集合）——没有这个参数，"限定范围"就只是提示词里的
一句请求，模型忘了就没了。

### 3.19 冒烟断言：让"答错"等于"空"

新加的 mention 检查第一版写成 `jq 'index($k)'`，返回 `0`——`check` 把 "0" 当失败，于是一个
**通过的功能被报成失败**。这条在 3.11 已经记过，还是又踩了一次。

写法固定成：`map(select(. == $k)) | length | select(. == 1)`。断言要么给出非零数字，要么
什么都不给，绝不给出 `0` / `false` 这种"看起来像答案的失败值"。

另外给 `smoke.sh` 的结尾加了**失败项名字汇总**——上一轮有四项失败滚出屏幕，只看到
"93 passed, 4 failed"，白白花了一轮去复现。

### 3.20 深分页：并列打破条件不在索引里，代价按走过的行数收

10 万条库、`offset=50000` 的一页要 **95.7ms**。拆开看是两笔账：

1. 每个列表都 `ORDER BY <列>, i.id`（让分页在同值时稳定），但六个排序索引都**只到排序列为止**。
   SQLite 于是用临时 B 树去处理最后一项——对它走过的**每一行**都要付，包括 offset 马上要
   丢掉的五万行。**这一项就占 88ms**（10.1 → 97.7）。
2. `LEFT JOIN items p` 求父条目 key，同样对那五万行都做了一遍。

两笔分别修：索引补上 `id`（方向保持一致即可，SQLite 会倒着读索引），查询改成**延迟 join**——
先只从索引里取出这一页的 100 个 id，再去取列。

结果：**95.7ms → 2.0ms**；offset=99000 时 42.5 → 3.7ms。首页不受影响（0.2ms）。

计划断言（`items::plan_tests`）：子查询区段内不允许出现任何 `TEMP B-TREE`。

### 3.21 计划断言写错字符串 ⇒ 一个永远不会响的警报

上面那个测试第一版断言的是 `TEMP B-TREE FOR RIGHT PART OF ORDER BY`，而 SQLite 在这里
说的是 **`LAST TERM`**。于是把索引换回旧定义、制造出**正是它要防的那个回归**，测试照样通过。

教训：计划断言写完必须**反向验证一次**——故意破坏，看它是否失败。匹配具体措辞不如匹配
"这一段里不该出现某类操作"，措辞会随版本变，代价是一个安静失效的保险。

### 3.22 基准数字里不全是查询代价

端点在 `offset=50000` 上 curl 只要 7ms，基准却报 43.5ms。差额不是查询——深处那一页的条目
本身字段更多，**响应体大 55%**（61.8KB vs 39.9KB），多出来的是序列化和 Node 侧的 JSON 解析。

所以优化前后要比的是同一个测量口径，而判断"还值不值得再优化"要看**分离出来的那部分**：
SQL 2.0ms、端点 7ms，说明剩下的账不在数据库上。

### 3.23 导入不能悄悄丢东西：独立笔记

Zotero 允许笔记不挂在任何论文下（阅读笔记、会议记录、草稿）。导入器的 SQL 写着
`WHERE itemNotes.parentItemID IS NOT NULL`，于是这些笔记**连同预览里的计数一起**被丢掉——
用户没有任何迹象可以察觉。而且当时还有一条测试**把这个行为固化下来了**
（"这里还没有地方放它"）。

丢用户的数据比慢一百毫秒严重得多。现在 `LEFT JOIN`，`parent: Option<Key>`，预览计数包含它们。

配套的两个细节：
- 笔记类型原本没有 `title` 字段，独立笔记会在列表里显示成一行空白。schema 加上 `title`，
  优先用 Zotero 自己存的摘要，没有就用 `note_title()` 取正文第一行。
- `note_title()` 必须区分**块级**和**行内**标签：第一版把 `</b>` 也当换行，
  `<b>Meeting</b> notes` 变成了 "Meeting"。

### 3.24 `#[serde(flatten)]` 会把任何键都收进来

`Item` 的字段是平铺到 JSON 顶层的。于是客户端 POST 一个看起来最自然的
`{"fields": {"title": "..."}}`，会得到一个**名叫 "fields" 的垃圾字段**，标题丢失，**而且不报错**。
我自己在调试时就踩了，还误以为是另一个 bug。

schema 里本来就有 `validate()` 能报出未知字段，只是没人调用。现在写入时未知字段直接**拒绝**并
列出名字。对 Word/Chrome 插件这种外部客户端，"存下来但永远不显示" 是最坏的失败方式。

### 3.25 429 是常态，不是故障

模型端返回 `429 + Retry-After: 1`，整轮对话直接变成 500 并丢掉已经做完的工作。限流是**会自愈**的，
服务通常还告诉你等多久。

重试放在 `yk-ai` 的 provider 里：只有这一层读得到 `Retry-After`，否则每个调用方都要写一遍同样的循环。
policy 是纯函数、可单测：429/502/503/504 值得等，400/401 等多久都没用；`Retry-After: 0` 至少睡 200ms
（否则是对着一个已经吃力的服务空转）；上限 20 秒（"等 5 分钟"是真话，但没人在一个请求里等五分钟）。

**同时**：冒烟测试必须能区分"模型此刻被限流"和"功能坏了"。共享端点饱和时把套件报成失败，
它就不再被相信——现在这几项会打印 `skip` 并说明原因。这也解释了之前那次莫名其妙的 "93 passed, 4 failed"：
就是同样这四项。

### 3.26 单测парsing 通过 ≠ 输入框接上了

`mentionQuery` / `stripMention` 有七条单测全绿，但**没有一条证明输入框真的调用了它们**。
补上渲染测试后立刻抓到一个真 bug：没有配置模型时走的是 `append` 分支，而那条路径
**完全没有传 mentions**——用户挂上去的论文静默丢失。（已反向验证：去掉修复，测试必然失败。）

规则重申：纯函数测试证明的是函数，证明不了接线。会发生交互的地方必须渲染出来点一遍。

### 3.27 `beforeEach` 没重置的字段，迟早会测到"泄漏"本身

同一次补测试还发现：`chat.render.test.tsx` 的 `beforeEach` 逐个列出要设置的 store 字段，
但没有列 `runs`。于是前一个 describe 留下的"运行中"状态一直在，`busy` 恒为真，
**所有发送都静默失效**——表现出来是"Enter 没反应"，查了半天才发现和被测代码无关。

写法：凡是测试会写入的 store 字段，`beforeEach` 都要显式复位，哪怕当前用例用不到。

### 3.28 网页端配不了模型，"一切通过网页端"就是句空话

设置页有外观、搜索、快速添加……**唯独没有模型**。用户只能去改 `config.toml` 再重启——
而这是个由用户自己启动的本地服务，让他去编辑文件重启，等于承认网页界面是残缺的。

现在 `PUT /agent` 保存配置并**原地重建 agent**（`AppState` 里的 config 和 agent 都放进
`RwLock`），不需要重启。三个细节：
- `agent()` 返回 `Option<Arc<Agent>>` 而不是借用：一轮对话比锁活得久，跨着 read guard
  等模型回答，会把所有重配置堵死。
- API key **只写不读**。返回的是 `hasApiKey: true/false`，永远不回传密钥本身。
- 因此 patch 必须区分"字段缺席"和"字段为空"：缺席=保持不变，空=清除。否则一个永远不显示
  密钥的表单，每次保存都会把它抹掉。
- `config.toml` 写临时文件再 rename——写了一半的配置文件，下次启动才会发现。

### 3.29 会写配置的冒烟检查，可能把后面的检查全带塌

新加的"半份配置应被拒绝"检查，第一版只发 `{"model": "only-a-name"}`。但那台服务的 endpoint
是环境变量给的，于是这**不是**半份配置——请求成功了，把模型名改成 `only-a-name` 并**写进了
配置文件**，后面四项 agent 检查随之全挂。

改成显式发 `{"endpoint": "", ...}`：既是真正的半份配置，又因为被拒绝而不会落盘。

一般规则：冒烟检查里任何会**写状态**的断言，都要问一句"如果它意外成功了，会破坏什么"。

### 3.30 两个界面没有渲染测试，两个都在崩

补齐 Plugins 和 Status 的渲染测试，两个都当场抓到**整块面板崩掉**：

- **Plugins**：`p.avgLatencyMs.toFixed(0)`。一个缺失的数字让所有插件从屏幕上消失。
- **Status**：`stats?.search.embedded`——可选链只保护到 `stats`，`search` 缺失照样崩。
  而这是"出问题时才会打开"的页面，最可能被看到的状态恰恰是它撑不住的状态。

两处都改成缺值显示 `—` 而不是崩。已反向验证：撤掉修复，测试必然失败。

规律很清楚：**没有渲染测试的界面，默认假设它是坏的**。到目前为止，每一个补测试的界面都抓到了 bug。

### 3.31 fixture 里字段"长得一样"，测试会点错卡片

插件测试一开始三个插件共用同一段描述和同一个贡献标签，于是
`cards().find(c => c.textContent.includes('Crossref'))` 匹配到了**别人卡片上的一个 chip**，
所有点击都作用在第一张卡上，报出来的却是 "expected 'broken' to be 'crossref'" 这种看不出原因的错。

fixture 里**每一个可见字段都要互不相同**。共用值省下的几行，会在定位失败时十倍还回去。

另外：mock 也要能承受被测代码引发的副作用。切换插件开关会触发重新拉取列表，
而 mock 的 `plugins.list` 返回空数组——页面看起来坏了，其实是 fixture 自己消失了。

### 3.32 一个页面只能有一个东西在滚

Downloads 出现两个滚动条：`.pane` 默认 `overflow: auto`，而里面的 `VirtualList` 自己也滚。
这不是 CSS 写错了一处，是**两个都对但不该叠在一起**——适合一页散文的容器，不适合装一个自带
滚动的列表。

现在有 `.data-page`（flex 列 + `overflow: hidden`）承担这类"页面就是一张表"的布局，
Downloads / Files / Gaps 三处统一。列表就是唯一的滚动体，表头在它内部 sticky。

顺带补齐的两件事：三个页面都加了**真正的表头**（列名要压在列上，而不是挨着列），
以及同一行内的操作按钮统一用同一个 tone——Retry 和 Remove 是同一类动作，
两种视觉语言会让人以为它们不是。

### 3.33 jsdom 里 `getComputedStyle` 什么也证明不了

给"只有一个滚动条"写测试时，第一版断言 `getComputedStyle(page).overflow === 'hidden'`——
失败了，因为 jsdom 根本不加载样式表，读到的是空字符串。**它不会因为 CSS 写对而通过，
也不会因为 CSS 写错而失败**，是个纯粹的噪音断言。

能测的是结构：页面根节点带的是 `data-page` 而不是会滚动的裸 `.pane`，且 `.vlist` 只有一个。
CSS 本身的正确性得靠看，不靠 jsdom。

### 3.34 改了结构，就要去删掉为旧结构写的 CSS

输入框被重做成"一个整体控件"之后仍然很丑，原因不在新样式，而在**旧规则还在生效**：
`.chat-input textarea { flex: 1 }` 和 `.chat-input button { align-self: stretch }`
是为"一行里放一个输入框和一个按钮"写的，现在里面是一个纵向的 composer，
于是发送按钮被拉成整个盒子那么高。

改结构时必须回头把为旧结构写的规则删掉。留着它们不会报错，只会让新布局以一种
"说不上哪里不对"的方式变丑——比一个明确的错误更难查。

### 3.35 会无限增长的列表，一律虚拟化

对话不是有界的：一个真正在用的 thread 有几百条消息，而**一次 tool call 的结果本身就可能
是几百行**。全量渲染是"打开旧对话很慢"的直接原因。

两个要点：
- 高度必须**测量**而不是假设。一行的回答和一份参考文献 dump 挨在一起，给不出统一行高。
  测量有代价（每行一次 layout 读），所以只在高度确实参差的列表上开。
- 实时进行中的那条消息**也要放进列表里**。放在滚动容器外面，它会和最后一条消息重叠。

### 3.36 长列表要能按"内容"跳，而不是按距离

几百条消息里，用户要找的是**自己问过的某句话**，中间的回答正是让滚动失效的东西。
所以右侧的导航条一条 tick 对应一个提问，hover 出预览，点击跳过去。

只在超过阈值（12 条）时出现。短对话上它是"在解释一个不存在的问题"的装饰。

### 3.37 jsdom 里 `mouseenter` 永远不会触发 React 的 `onMouseEnter`

React 的 `onMouseEnter` 是用委托的 `mouseover` 合成的，而 `mouseenter` **不冒泡**，
派发它永远到不了处理函数。测试里要派发 `mouseover` 并带 `bubbles: true`。

同一族的坑还有：`getComputedStyle` 在 jsdom 里读不到样式表（见 3.33）。
凡是"浏览器帮你做的事"，在 jsdom 里都要先确认它到底做不做。

### 3.38 客户端虚拟化了，服务端还在整包发，等于只做了一半

上一轮把消息列表虚拟化，但 `GET .../messages` 仍然**一次返回整个 thread**。
300 条消息 275KB，而这只是中等规模——真实的 agent 线程里，一次 `read_file` 的结果
就可能有几十 KB，几十次工具调用轻松堆到几 MB。

现在按页取（默认 60 条，`before=<id>` 往回翻），打开对话的代价与 thread 长度无关：275KB → 55KB。

两个实现细节值得记：
- SQL 要写成 `ORDER BY id DESC LIMIT n` 再反转，而不是"全取出来再截最后 n 条"——
  后者会把整个 thread 读出来再扔掉。
- 多取一行来回答"还有没有更多"。用"这一页满了"来推断，**恰好在 thread 长度是页大小整数倍时是错的**。

### 3.39 更严重的是：每轮都把整个历史发给模型

同一处代码里发现的真问题——`run_turn` 把**全部**消息塞进 prompt。thread 越长，
每一轮越贵，最终必然超出上下文窗口。

现在限制在最近 40 条。丢掉开头是安全的，**因为常驻事实（对话绑定的 collection、
被 @ 提及的论文）已经由 `turn_context` 每轮重新陈述**——这正是当初把它们做成独立
system message 而不是塞在历史里的原因。

### 3.40 改了线格式，就要去改所有读它的地方——包括冒烟脚本

`messages` 从数组变成 `{messages, hasMore}` 之后，编译器帮我抓到了 Rust 侧，
TypeScript 帮我抓到了前端，但**冒烟脚本里的 4 处 `jq` 只有运行时才会发现**——
其中 3 处在那一轮直接报失败。

线格式的变更清单必须包含：Rust 测试、前端 mock、`jq` 断言。前两个有编译器兜底，
第三个只有跑一遍才知道。
（另外这也再次说明冒烟脚本值得留着——它是唯一会以真实 HTTP 形状检查这些的东西。）

### 3.41 "列表变长了" ≠ "末尾多了东西"

给对话加了分页之后，紧接着自己埋了一个 bug：跟随末尾的逻辑写的是
`setJumpTo(count - 1)`，依据是**条数变化**。而加载更早的消息让列表在**另一端**变长——
于是用户每点一次"加载更早"，就被甩到整个历史的底部，正是他要往回找的东西被扔掉。

规则：**末尾要用"末尾是什么"来识别，不能用"前面有多少个"**。抽成了纯函数
`shouldFollow(previous, next)`，只在三种情况下跟随：首次打开、最后一条的 id 变了、
进行中的那条又长高了（同一条，但底部确实动了）。

第二半同样重要：内容加在上方会把视图整体推走，所以要**保持锚点**——
记住原先的第一条，加载完再跳回它。少了这一步，"看历史"变成"被扔进历史中间"。

这类 bug 的共性：**功能本身是对的，坏的是"什么时候触发"**。纯函数 + 单测是唯一能
在写的时候就想清楚的方式，等到手动点一遍才发现就晚了。

### 3.42 结果没人看得见，等于没发生

"生成摘要"从做出来那天起就是好的：调模型、写成一条子笔记、挂在论文下面。
但**界面上没有任何地方显示这条笔记**——用户得自己知道去翻子条目。
详情面板有参考文献、有相关对话，偏偏没有笔记。

一个不被展示的结果，和没产生这个结果，在用户那里是同一件事。

顺带把摘要笔记**标记出来**：模型写的摘要和用户自己写的笔记，是两种不同可信度的东西，
放在一起不加区分是在替用户做判断。

### 3.43 慢操作必须在**开始**时就说话

`withToast` 只有成功/失败两种消息。而它包住的有些是**跑将近一分钟的模型调用**——
整个过程界面一声不吭，而"点了没反应"是对这种沉默最自然的解读。

加了可选的 `pending`：开始时推一条，结束时（无论成败）撤掉。
失败路径也必须撤——一条留在屏幕上的"正在生成…"比没有更糟，它在说东西还在路上。

### 3.44 加 i18n 词条前先 grep

这一轮加词条撞了**两次**重复键（`detail.notes`、`summary.working`），
都是 TypeScript 报的 `TS1117` 拦下来的。词条表已经四百多条，凭印象判断"这个应该还没有"
是不可靠的。

好在编译器兜得住——但这也说明**词条表值得保持类型化**（`t()` 的参数是联合类型），
换成 `Record<string, string>` 的话这两次都会变成运行时才发现的重复覆盖。

### 3.45 修了一处慢操作，就要把同类的都找出来

上一轮给"生成摘要"加了进行中提示，**只改了那一处**。这一轮去看其他 `withToast` 调用点，
发现**重建搜索索引在 10 万条目上要 29 秒，全程一声不吭**——和摘要是同一个问题，
而且它还在三个地方（设置页、状态页、命令面板）各接线一次，每处抄了一份文案。

三份沉默半分钟的按钮，就是三次"这按钮是不是坏了"的机会。

现在收进 `lib/maintenance.ts`：**一处定义、三处调用**。

一般规则：修掉一个模式的实例之后，立刻去找同一个模式的其他实例。
只修当下那一处，等于把同样的 bug 留在原地并且从此更难被发现——因为"这个我修过了"。

### 3.46 测试里的文案要从词条表取，不要凭记忆写

新测试断言 `'Database compacted'`，实际词条是 `'Database optimised'`。
断言里写死用户可见字符串本身就脆，凭印象写更是必错。

（这次直接失败所以立刻发现了；危险的是反过来——断言写成 `toContain('Database')`
那种"看起来能过"的模糊匹配，就会一直绿着而什么都没测。）

### 3.47 冷启动的唯一卡顿，是一份反正要算的东西

量了一遍打开应用时发的全部请求：除 facets 外全部亚毫秒，而 **facets 首次 227ms**，
之后 0.7ms。这是缓存模块自己写明的行为——冷缓存不供陈旧数据，因为没有旧答案可供。

但这份计算**反正要做**。提前在后台做，不多花任何代价，却拿掉了冷启动里唯一能被感知的停顿。
227ms → 1ms。

### 3.48 预热用的参数必须来自调用方，不能来自类型的 `Default`（踩了两次）

第一版预热毫无效果。原因不是没跑，而是**键不一样**：缓存键包含 filter 的每一个字段，
而路由里 `recursive: self.recursive.unwrap_or(true)` 默认 **true**，
`ItemFilter::default()` 却是 **false**。于是预热填了一个没人会问的槽位，
真实请求照样付全价。

修法是用路由自己的转换（`ListParams::default().filter(lib)`），而不是手写一个 filter。

这和 13 节末尾"测试指纹必须是真指纹"是同一个错误：**照着类型写，而不是照着调用方
真正发送的内容写**。缓存和测试在这一点上完全一样——键对不上，两者都会安静地什么都不做。

### 3.49 用自己的请求验证，等于没验证

上一轮修完 facets 预热，我用 `curl "?limit=60"` 量到 227ms → 1ms，宣布搞定。

**侧边栏实际发的是 `limit: 80`。** 我恰好用了和预热相同的 60，于是命中了一个
只有我自己会请求的键。客户端的真实请求依然是 **264ms**——预热对它毫无作用。

同一个功能上，同一类错误犯了两次：
- 第一次：filter 照着 `ItemFilter::default()` 手写（`recursive` 差一个 bool）
- 第二次：验证时用自己顺手写的参数，而不是客户端真正发送的参数

**验证性能修复时，请求必须逐字取自调用方。** 差一个参数，缓存就静默落空，
而"功能仍然正常"会让人以为修好了。

结构上的了断：facet 的默认条数只在服务端定义一处（`FACET_LIMIT`），客户端**不再传 limit**，
预热用的就是同一个常量。两个数字就是一次必然发生的漂移。
另加一条前端测试锁住"侧边栏不得自带 limit"，已验证：把 `limit: 80` 加回去，测试立刻失败。

### 3.50 预热连着落空三次，说明该做的不是预热

把首屏**全部**请求按客户端原样量了一遍（这次学乖了），发现 `stats` 冷启动 **303ms**。
第一反应是照 facets 那样预热——加进去，仍然 327ms。第二次预热也没打中。

停下来看代码才发现真相：`stats` 为了得到"库里有多少个标签"，调用的是
`tags.list(lib, None, 100_000).len()`——**把 33 个标签连同各自的计数全聚合出来**
（对 13 万条目的 `item_tags` 做 group-by），只为读一个 `.len()`。
而 `SELECT count(*) FROM tags` 是 **0.01ms**。

改成 `TagRepository::count()` 之后：**303ms → 9ms**，整组冷启动请求全部落在 10ms 以内。

规律：**当"加缓存/加预热"反复不奏效时，多半是这件事根本不该做。**
预热是把必要的工作提前；它治不了"这份工作本身就是多余的"。
两个问题看起来一样（都是"某个请求很慢"），但一个的答案是提前算，另一个的答案是别算。

### 3.51 `list().len()` 是个信号

上一轮修掉 `tags.list(...).len()` 之后，去找同一形状的写法，
在同一个 `stats` 里找到第二处：`collections.list(lib).len()`。
合集列表会给**每个**合集附上成员数——一次对 `collection_items` 的完整遍历——
而调用方只想要"有多少个合集"。

这次先量了才改（项目自己的规矩）：基准库里合集为空，量出来 0.33ms，看着无所谓；
造出 4500 条归属关系后是 1.29ms，线性外推 10 万条归属约 **29ms**。
也就是说这个缺陷**只会伤到库大的用户**，而在开发机上永远量不出来。

`Repository::count()` 现在是标签和合集各自的一等方法。

一般化：**`.len()` 接在一个会做聚合的 `list()` 后面，几乎总是个 bug。**
它在小数据上完全正常，所以既不会被测出来，也不会被注意到——直到某个人的库长大。

顺带一条测试里写下的边界：`tags.count()` 数的是**行**，而 `tags.list()` 会滤掉
没有存活条目的标签。两个数字允许不一致，所以测试里明说了这一点，
免得将来有人"顺手对齐"它们。

### 3.52 基准跑错了服务器，而它一句话都没说

`bench.mjs` 的地址取自 `process.argv[2]`，默认 `23130`，**完全忽略 `YK_PORT`**。
而运行手册和我自己一直写的是 `YK_PORT=23140 node scripts/bench.mjs`。

也就是说：**过去很多轮里我报告的基准数字，量的都是冒烟服务器**，不是基准库。
更糟的是这一轮新加的 shelf 种子把 230 个合集和几万条归属关系写进了冒烟库。

发现它靠的是一个矛盾：`stats` 说 230 个合集，而 `GET /collections` 只返回 1 个——
同一个"库"给出两个数字，只能是两个不同的数据库。

修法有两条，都必要：
- 脚本认 `YK_PORT`。**一个静默忽略你给的变量的脚本，会安静地量错几个星期。**
- 每次运行打印它连的是哪个地址。事后无法归因的测量，等于没有测量。

### 3.53 合集筛选：`EXISTS` 读起来自然，跑起来是反的

"属于这个合集的条目"最自然的写法是
`EXISTS (SELECT 1 FROM collection_items ci WHERE ci.item_id = i.id AND ...)`。
它让 SQLite 从 `items` 那侧驱动：走遍全库十万行，对每一行去探测归属表。

改成 `i.id IN (SELECT ci.item_id FROM collection_items ci WHERE ...)`，
驱动方向反过来——先把这个合集的成员物化一次，再去探 `items`。
**41.8ms → 2.0ms，结果完全相同。**

和 `graph::TAG_SQL` 里那句 `CROSS JOIN` 是同一个道理，也同样只有计划断言能守住。

### 3.54 基准的语料不像真实的库，就看不见真实的缺陷

10 万条目、**零个合集**——那不是一个文献库，那是一份列表。
"按合集浏览"这条最常用的导航路径，因此从来没有被基准测过；
而上一轮那个 29ms 的合集计数缺陷，在没有归属关系的语料上量出来是 0.33ms，看着毫无问题。

种子现在会建 40 个合集（含嵌套）并把六成条目归档进去，并新增三项测量：
单个合集、含子合集、以及 `stats` 本身。

### 3.55 冒烟测试跑在旧二进制上，会报出一个假故障

改完 `hydrate` 让列表带上附件标记，冒烟里的新检查报 `attachments` 为 `null`。
先怀疑了序列化、`skip_serializing_if`、`parentKey` 解析——都没问题：
23130 端口上跑的还是改动之前编译出来的 `yinkote`，进程是几轮之前起的。

这和 3.52「基准跑错了服务器」是同一类错误的两种长相：**测量对象和被测代码不是
同一份东西**。区别在于基准是连错了地址，这里是连对了地址、跑的是旧代码。

规矩：**改过服务端就先 `cargo build --release` 再重启常驻进程，然后才跑冒烟。**
排查这类问题的最快提问不是"代码错在哪"，而是"我此刻测的，真是我刚写的吗"。

### 3.56 造一个新控件之前，先问它是不是已经有了

对话框底部的 scope 下拉框在深色界面里是一块白的——因为它是裸的 `<select>`，
而 `ui/controls.tsx` 里的 `Select` 早就存在，界面别处的下拉框用的都是它。
没有人"决定"要个白框，只是写的时候没想起来共享控件。

浏览器默认样式和这套界面没有半点关系，任何裸的表单元素都会当场穿帮。
**加 `<select>`、`<input>`、`<button>` 之前先在 `ui/` 里搜一遍**；
穿帮的地方，答案基本都是"共享组件本来就有"。

### 3.57 时隐时现的控件比一直都在的控件更难用

跳转轨（`JumpRail`）原先设了 12 条消息的阈值，理由写得很像样：短对话里它是
"给不存在的问题做解释"。真用起来是另一回事——它在对话进行到一半时毫无预告地
冒出来，而在此之前用户根本不知道有这个东西。

**一个控件的位置固定，才谈得上依赖它。** 省掉几像素的代价，是用户要重新学一遍
界面。空对话没有问题可指，那才是唯一该隐藏的情形。

顺带两条命中率很高的细节：
- 2px 高的刻度点不可能点得准。用 `background-clip: content-box`，让 padding 变成
  透明的命中区（视觉 2px，实际 9px），再在 hover 时把刻度本身放大。
- 悬浮预览要贴着**被指的那个刻度**（`top` 取 `e.currentTarget.offsetTop`），
  固定高度的预览框会让人分不清它在说哪一条。

### 3.58 派生字段就别存

"这一行有没有 PDF"是从子附件算出来的，每次读取都算，不落库。存一份摘要意味着
多一个会和真实附件对不上的东西——附件删了、加了、换了类型，都得记得同步。

算的成本是可以量的：一页 100 行多一条 `parent_id IN (...)` 的查询，走
`idx_items_parent`，**0.02ms**。这和标签、合集那两趟是同一个形状——
一页一次，不是一行一次（后者是 3.x 里反复出现的那个错误）。

### 3.59 冒烟断言要照着接口真实的形状写

新加的检查用 `jq -r .key` 取新建条目的 key，而 `POST items` 是批量接口，
返回的是 `{"created":[...]}`，于是拿到 `null`，报了第二个假故障。

- **先 `curl -i` 看一眼真实返回**，再写断言。文件里别处早就用的是 `.created[0]`。
- `check` 只判断非空（见 3.12 末条），**相等要用 `jq ... | select(. == "…")` 表达**，
  多传一个"期望值"参数是没用的，它根本不看。
- jq 程序写在单引号里，**行尾反斜杠不是续行**，是喂给 jq 的非法字符。要么写成一行，
  要么关掉引号再续。

### 3.60 一次 `stat` 一微秒，包住它的 `await` 五十微秒

文件浏览器一页 500 行要 29ms，而找出这 500 行的 SQL 只要 **0.4ms**。慢的不是
数据库——是每行一次 `tokio::fs::metadata(...).await`，一个接一个地等。

`tokio::fs` 的每次调用都是一次到阻塞线程池的往返。系统调用本身是微秒级的，
往返不是。**整页一次 `spawn_blocking`、里面用 `std::fs` 顺序跑**，
29.1ms → 10.4ms。

规矩：**异步文件接口适合"偶尔一个文件"，不适合"一页文件"。** 循环里出现
`.await` 的 I/O，先问这一批能不能一次交出去。同理，这类批量接口要按顺序返回，
让调用方能按下标对回去，而不是返回一个还要再查一遍的 map。

### 3.61 已经 JOIN 到的行，别再查一遍

`attachments()` 的语句里本来就有 `LEFT JOIN items p ON p.id = i.parent_id`，
但只从中取了 `p.key`；随后又用 `key IN (…)` 分 34 批把三万个父条目重新捞了一遍
（**106ms**），还得自己维护分块逻辑防止撞上 SQLite 的变量上限。

父条目的每一列都在那次 JOIN 的射程之内，多取几列只多几个字节。改成一条语句后
rename preview 497ms → 321ms，同时删掉了整块分块代码。

规矩：**写第二趟查询之前，先看第一趟的 JOIN 是不是已经站在那张表上了。**
这类重复不会有任何测试报错——两条路都能得出正确答案，只是其中一条白跑。
（守住它的办法是断言父条目的**字段**回来了，而不只是 key 回来了。）

### 3.62 一次批量操作是一件事，就该是一个事务、一个版本号

改文件名的写入路径是"每个文件一次 `update`"，而每次 `update` 都自开一个写事务、
自增一次库版本号。实测单条 0.41ms（进程内）/ 3.91ms（走 HTTP），三万个文件就是
**两分钟**，还在版本历史里留下三万个版本号——同步时要发的增量因此白白胀了三万倍。

新增 `update_many`：一个事务、一个版本号，每行一个 savepoint（照抄 `create_many`
的形状，一行失败不牵连整批）。单条 0.41ms → **0.121ms**，版本号 500 → 1。

规矩：**循环里出现"每次都自开事务的写操作"，就是找错了接口。** 和 3.60 是同一
条思路的两个面：那条说的是循环里的 `await` I/O，这条说的是循环里的事务。

顺带一个语义上的好处：agent 的批量打标签原先是 `get`+`update` 逐条来，某个条目
被删掉就整条指令报错；换成 `get_many`+`update_many` 之后，失败的是那一条，
不是整批。**批量接口天然该按行报告结果**，这也是 `Vec<Result<Item>>` 这个返回
类型看着啰嗦却必须如此的原因。

### 3.63 `scrollTo` 是一个请求，不是一个状态

列表往下滚、加载下一页、**啪一下弹回最顶上**——每加载一页都这样。

`VirtualList` 里那个 effect 是：

```ts
useEffect(() => {
  if (rows.length && scrollTo !== undefined) virtual.scrollToIndex(scrollTo)
}, [scrollTo, rows.length, virtual])   // ← rows.length
```

`rows.length` 在依赖里，于是**追加一页就重跑一次**。而表格传进来的 `scrollTo`
是键盘光标，没用过键盘的人光标就是第 0 行——所以每次加载都把人送回第一行。

这和 3.x 里聊天"加载更早的消息反而跳到底部"是**同一个错误**：把"列表变长了"
当成了"用户要求滚动"。列表变长是结果，不是意图。

规矩：**请求型的 prop 要记住自己有没有被执行过**，用一个 ref 记下已兑现的值
（`shouldScroll(request, honoured, rowCount)`，提成纯函数才测得了）；同时它得
熬过"请求先到、数据后到"——恢复位置时要滚的那一行还没加载出来，所以未兑现的
请求要留着，而不是当场丢掉。

### 3.64 原生 `<select>` 的弹出层，颜色来自控件自己的 background

上一轮把对话框的 scope 下拉框换成了共享的 `Select`，**它还是白的**。
换组件没错，但 `.chat-scope select` 里有一条 `background: none` 一直在生效：

Chromium 画 `<select>` 弹出的那个列表时，用的是控件自身的 background；
一旦作者把它写没了，弹出层就退回浏览器默认的白色——`:root { color-scheme: dark }`
在这种情况下救不回来（它只管作者没插手的部分）。

真正管用的是**给 `option` 本身上色**，而且这条规则属于全局控件样式，不属于某一个
下拉框：所有原生 select 都有这个毛病，写在一处才不会下次又漏一个。

判断这类"样式没生效"的问题，别停在"我换成共享组件了"——要问**旧规则是不是还在
匹配这个元素**。这里 `.chat-scope select` 是元素选择器，换了组件照样命中。

### 3.65 规则算对了，结果什么也没发生

上一轮修好"加载更多不该滚动"之后，顺手复查了同一族的其它 effect，发现了一个
更安静的毛病：`shouldFollow` 里明明写着

```ts
// Same last entry, but the live turn grew — its own height changed, so the
// bottom moved even though nothing was added.
return next.steps > previous.steps
```

判断完全正确，而它触发的动作是 `setJumpTo(entries.length - 1)`——流式回答长在
**同一个条目里**，下标没变，于是 React 认为 state 没变、effect 不重跑、
**日志不跟随**。规则算对了，结果一路被丢掉，而且没有任何报错。

根因是用一个 `number` 同时表达了两种意图：

- **位置**："把光标那一行留在视野里"。同一行要求两次，第二次没有新意思。
- **命令**："现在滚到底"。同一行要求两次，就是两次请求。

裸下标只能表达前者，聊天要的是后者。改成 `ScrollRequest { index, token }`，
由 token 区分"又一次请求"和"同一个请求被重放"——这同时也修好了"同一个跳转刻度
点两次没反应"。

规矩：**当一个值既被当作状态、又被当作命令时，它总会在其中一头出错。**
判断逻辑写得再对也救不回来，因为错误发生在它下游。看到"这个 setState 传的是
算出来的同一个值"，就要立刻警惕。

### 3.66 计划断言跑在没有统计信息的空库上，也是一个不会响的警报

给全库查重加了 `INDEXED BY` 之后，按 3.21 的规矩反向验证——**去掉提示，断言照样通过**。

原因不在断言写错，而在测试库和生产库面对的**不是同一个规划器**：
`PRAGMA optimize` 会在真实库里留下 `sqlite_stat1` / `sqlite_stat4`，规划器是拿着
数字在选路；而 `Store::in_memory()` 是空表，只能靠启发式。同一条 SQL，
13 万条的真实库选 `idx_items_parent` + 两棵临时树，空库自己就选中了指纹索引。

补救分两层：
1. 计划测试先灌入几千行**形状接近**的数据再 `ANALYZE`，让规划器有可比的依据；
2. 仍然反向验证。本例灌到 4 万行、规划器依旧自愿选对，说明这条断言在测试规模下
   **抓不到**去掉提示的回归——于是把这句话写进测试的文档注释里，而不是留给
   后人以为警报是布防的。

规矩：**"断言通过"和"断言有效"是两回事。** 每条计划断言都要能说出它在什么规模下
有效、在什么规模下只是摆设。

### 3.67 指纹优先取标识符，于是最常见的那种重复反而配不上对

查重上线后，冒烟里"合并后这一组应该消失"通过了，"应该发现这一组"却没通过。
原因是造的两条数据一条有 DOI、一条没有：`Item::fingerprint` 优先用 DOI，
两者指纹根本不同——而"一份从出版商导入、一份手工录入"正是最常见的重复。

所以查重必须**两把尺子**：按标识符分组，再按题名/首作者/年份分组（这三列早就为
排序反规范化好了），一个条目命中任意一把即入组。两组还会交叠（A、B 共 DOI，
B、C 共题名，其实是同一篇的三条），必须**按 id 求并集**，否则 B 会出现在两组里，
诱使人把它合并进两个不同的主记录。

这条更一般的形状是：**一个"规范化的键"总是为某个用途设计的**，拿它去做另一个
用途时，先问它在什么情况下会把该相等的两样东西算成不等。

### 3.68 冒烟库是留下来的，固定的夹具会在第二次运行时说谎

同一轮里第二个假故障：合并之后那一组还在。因为夹具标题写死，而 `/tmp/ykfinal`
跨轮保留——上一轮造的同名条目还在库里，本轮的记录和**历史遗留**又组成了新的一组。

规矩：**在保留的数据库上做冒烟，凡是靠"数量/存在性"断言的夹具都要每轮唯一**
（进程号 + 时间戳足够）。否则测试会随着运行次数逐渐变成另一个测试。

### 3.69 断言"数一数"之前，先确认两边数的是同一样东西

冒烟里"备份可恢复"这一条报错：备份里 100837 条，实时库 101001 条。看着像备份丢了
数据——实际上备份完全正确，是**两个问题问得不一样**：`items?limit=1` 的 `total`
和我在备份里写的 `WHERE deleted=0 AND parent_id IS NULL` 对"算不算子条目、算不算
回收站"的口径不同。

换成**点名**就没有这个问题：本轮早先创建的那条 `$KEY`，要么在备份里，要么不在。

规矩：**跨两个系统比数量，是在同时赌两边的过滤语义一致。** 能点名就别点数；
真要数，两边必须是同一条 SQL。这类假故障最贵的地方在于它把人引向"备份坏了"，
而不是"我的断言写歪了"。

### 3.70 返回"该删哪些"，而不是"该留哪些"

备份保留规则（近 N 份 + 每月一份）写成了 `prune(names) -> 要删除的`。反过来写
——返回幸存者、删掉其余——读起来更自然，但两者的失败方式完全不对称：

- 返回幸存者，函数写错 ⇒ **删掉了不该删的备份**；
- 返回待删项，函数写错 ⇒ 磁盘上多留了几份没用的文件。

只有一种是能挽回的。**凡是"算出来的结果会直接导致删除"的函数，都让它的默认失败
方向是少删而不是多删**，并且明确跳过一切不认识的文件（用户自己放进备份目录的东西
不归我们删）。

### 3.71 保留规则要保住的是"出事之前"的那一份

"只留最近 N 份"是个很容易写、而且完全没用的规则：人发现数据出问题，往往是一个月
以后。所以规则必须是 **近 N 份 + 每月各留一份**——测试里直接写成"一年的每日备份
之后，还剩 7 + 11 份"，把这个意图钉死。

### 3.72 `get_many` 回答的是"哪些"，不是"按什么顺序"

导出复用了 `items.get_many`，而它是 `IN` 查询——返回顺序由索引决定，不是调用方
给的顺序。对编号型书目来说，这就是**静默重排别人的参考文献**，正是
`yk_cite::bibliography` 宁可不排序也要避免的那件事。

抽成 `routes::items_in_order`：取回后按调用方给的 key 顺序重排，取不到的丢掉
（导出一批刚好含有已删条目的选择，应该给出其余的，而不是整个失败）。顺带把
`render` 也换过去——它原先是每个 key 一次 `get`，顺序对但要 N 次查询。

规矩：**接口名里没有"order"，就不要假设它有顺序。** 尤其当调用方的顺序**本身
携带信息**时（引用先后、用户选择的次序），要么在文档里写明，要么自己重排。

### 3.73 导出格式写错，坏的不是那一条，是整个文件

BibTeX 里一个裸的 `%` 会把该行剩下的部分注释掉，一个不配对的 `{` 会吞掉它之后的
所有内容——**一条标题里带百分号的记录，能让整份参考文献编译不过**。RIS 同理：
最后一条没有 `ER  -`，多数导入器会直接丢掉它；值里带换行会变成解析器读不懂的标签。

所以导出的测试不能只测"字段对不对"，要测**这些会破坏文件的字符被转义了**、
**每条记录都正确终止了**。冒烟里还加了一条"花括号配对"——它检查的不是内容，
是文件还能不能被解析。

另一条相关的：**空字段要整条省略，不能写成 `volume = {}`**，导入器会把空串当成
一个真实的卷号。

### 3.74 单个文件名写进配置，下一个人就会踩同一个坑

`vitest.config.ts` 里 jsdom 环境原先是 `theme.test.ts` 加 `*.render.test.tsx`。
新写的 `download.test.ts` 要用 `document`，症状是 `document is not defined`，
而原因在一个没人会想到去看的配置文件里。

改成后缀约定 `*.dom.test.ts`。**凡是"想启用某种能力就得回来改配置"的清单，
都要换成一条可自解释的命名规则**——否则每加一个文件就要重新发现一次。

### 3.75 有了导出器，最值钱的测试是"自己写的自己读得回来"

导入 BibTeX/RIS 时写的第一条测试不是"能不能解析出版商的文件"，而是
**用自己的导出器造一条含有 `100% of {Braces} & other_things` 的记录，导出再导入，
断言字段一模一样**。这一条同时守住两边：转义写漏了，往返就对不上；反转义写多了，
也对不上。冒烟里再走一遍 HTTP，端到端。

规矩：**一对互逆的操作，往返属性比两边各自的单元测试都强**——因为它不需要你
预先知道正确答案长什么样，只需要两边对同一件事的理解一致。

### 3.76 解析别人的文件，宽容不是妥协而是需求

`.bib` / `.ris` 由几百个程序生成，其中相当一部分是错的：少一个右花括号、
RIS 记录不写 `ER`、摘要换行不重复标签。**因为第 11 条坏了就拒绝整个 40 条的文件，
对用户毫无帮助**。所以：坏记录逐条报告（带"第几条"，按记录数而非行数计，
因为用户能找到的是"第三条"），其余照常导入，接口回答 "38 imported, 2 skipped"。

两个具体的坑，都来自"显而易见的写法"：
- **按 `@` 切分条目**会把标题里含 `@someone`、URL 里含 `a@b.c` 的记录拦腰截断。
  要数花括号。
- **按逗号切分字段**会把 `title = {Cities: London, Paris, and Rome}` 切成三段。
  同样要看嵌套深度。

还有一条价值判断：**没有标题也没有作者的记录，宁可拒绝也不要导入**——
导进去就是一堆空行，用户还得自己找出来删掉。

### 3.77 格式要从文件内容判断，而不是从扩展名

从出版商站点下载的引文常常叫 `citation.txt`。让用户先回答"这是 BibTeX 还是 RIS"
是把程序能自己解决的问题推给人：RIS 一定以 `TY  - ` 开头，认它就够了。

### 3.78 输入框的值从 store 反推，就等于禁止用户打空格

搜索框里打不出 `attention is all you need`——**第一个空格就被吃掉了**。

链条是这样的：输入框的 `value` 来自 `parseQuery(query)` 再 `.join(' ')` 反推出来的
`draft`。分词再重组是**有损**的：尾随空格不是词与词之间的标点，而是"我刚打了一个
空格"这件事本身，`join` 之后它就没了。于是每敲一个空格，值立刻被规范化回去。

同一处还藏着第二个 bug：chips 是"query 里所有非 text 的 token"，于是 `tag:t` 刚打到
一半就被当成已完成的 chip 抽离输入框，下一个字符另起一段，query 长成
`tag:t tag:tr tag:tra`——标签算子根本没法逐字输入，联想也永远不触发。

两个 bug 一个根因：**"何为已完成"被写了两遍**。`splitCommitted` 本来就定义了它
（尾随空格才算完成，并且**刻意保留**那个空格），而 chips/draft 那里另写了一套。
改成两边都用 `splitCommitted`，两个 bug 一起消失。

规矩：**受控输入的值必须能逐字符还原用户所打的内容。** 任何"解析→重组"的往返都
会丢掉一些东西，而丢掉的那部分正好是用户正在打的那个字符。

### 3.79 触发器里写聚合，把批量插入变成了 O(N²)

给附件排序加了反规范化列 `attachment_rank`，用触发器维护（因为写入路径有五条，
漏掉一条是看不见的）。方向对，写法错：INSERT 触发器里重算
`max(...) FROM items WHERE parent_id = ...`——**插入第 N 个附件要扫前 N-1 个兄弟**。
一个一秒的测试变成了跑不完（>60s）。

修法是看聚合的方向：**加一个孩子只可能抬高最大值**，所以
`max(attachment_rank, <这一行的分值>)` 就够了，O(1)。只有 UPDATE / DELETE 会让
最大值下降，那两条才需要扫兄弟——而它们是罕见方向（文件成批加入，逐个修改）。

规矩：**触发器里出现聚合查询，先问它是不是可以增量。** 单条写入看不出问题，
批量导入才会现形，而那正是没人盯着的时候。

顺带一条：**改一个已经跑过的迁移文件，不会重跑**（按序号记录版本）。开发用的
常驻库要手工补上差异，否则你测的是旧 schema——和 3.55「跑在旧二进制上」同一族。

### 3.80 标注挂在附件上，不挂在文献上

"把这篇文献的标注汇成笔记"，最直觉的实现是取这篇文献的子条目——**结果永远是空的**，
因为那一层是 PDF，标注是 PDF 的子条目。要往下走两层。

这类"层级差一层"的错误不会报错，只会安静地返回空结果，所以冒烟里专门有一条断言
笔记确实挂在**文献**上、且真的收到了两条标注。

顺带两条渲染上的判断：
- **原文用 `<blockquote>`，读者自己的批注用 `<p>`。** 把两者混在一起排版，是个
  看起来很贴心的抄袭陷阱。
- **页码解析不了（`iv`、`12-13`）时不要丢掉这条标注**，排到最前即可——丢掉的是
  读者的劳动，排错位置他自己看得见。

同理，"既没有原文也没有批注"的空标记要丢掉：一个什么都不说的条目，比少一个条目更差。

### 3.81 阅读进度不能写在条目上

"重开 PDF 回到上次的位置"，最省事的实现是把页码存进附件条目的字段里。**不能这么做**：
条目一写就会自增库版本号，而版本号是同步和缓存失效的依据——于是**读一篇文献看起来
就像编辑了一次文献库**，滚动几下就是几十个版本。

存进 settings 表（`reader.<key>`）即可：没有迁移，没有版本号扰动。冒烟里专门断言
"写了阅读状态之后库版本号不变"——这条断言保护的不是功能，是**整个同步模型**。

一般规律：**高频、私有、不需要同步的状态，不要放进会产生版本号的地方。**

### 3.82 会偶发失败的闸门，等于教人忽略失败

agent 那两条冒烟检查偶尔会红——共享模型被限流（429），而脚本的限流预检是在检查
**之前**跑的，预检通过、真正那一次请求却被限流。

本身不是 bug，但后果很坏：**一个会无故变红的闸门，第三次之后就没人认真看了**。
改成从 run 的结果里认出限流并 `skip`（带原因），而不是 `check` 失败。

规矩：**外部依赖不稳定时，测试要能区分"它坏了"和"它现在不可用"**，并把后者
明确说出来。装作没这回事，和把它算成失败，都会让这套闸门失去意义。

### 3.83 冒烟各节之间不要有隐式的先后依赖

新加的一节引用了下面某节才定义的 `$NFILE`，于是 `unbound variable`。它本可以更隐蔽：
如果那个变量恰好在上面被定义过，这一节就会**悄悄测到别的东西**。

规矩：**一节要用的夹具就在这一节里造。** 顺序是编辑器里的偶然，不是契约。

### 3.84 加一个索引，改坏了另一条毫不相干的查询

上一轮为附件排序加了 `idx_items_attachment(library_id, deleted, attachment_rank, id)`。
它和 `idx_items_modified(library_id, deleted, date_modified, id)` **前导列相同**，
规划器改用了新的那个，然后把已经排好的顺序丢掉、对 13 万行做临时排序：

| | 之前 | 之后 |
|---|---|---|
| 首页 | 9.0ms | **68.6ms** |
| 深翻页 | 9.1ms | **108.3ms** |
| 标题排序 | 8.7ms | **55.7ms** |

**结果完全正确**，所以没有任何功能测试会红。这是本项目第五次栽在同一件事上
（8.5 秒的 `MISSING_SQL`、1585ms 的 `CITES_SQL`、查重、合集筛选，现在是浏览）。

规矩：**新增索引要当成对既有查询计划的一次改动来审**。凡是与既有索引共享前导列的，
必须重跑基准——单元测试和冒烟都看不见它。修法是给浏览查询显式 `INDEXED BY`：
每个排序字段都有一条"已经排好序"的索引，`filter::sort_index` 把这个映射写在一处。
只对**纯浏览**加提示；带标签/合集筛选时，筛选可能远比排序更有选择性，交给规划器。

### 3.85 计划断言把 SQL 抄了一遍，于是它守的是一条没人执行的语句

`plan_tests` 里的 `list_sql` 是手抄的一份 `list` 的 SQL。加提示那天，两者当场分叉——
测试**依旧通过**，因为它对着自己抄的那一版做断言。

规矩：**断言执行计划，必须让被断言的语句和被执行的语句出自同一个构造函数。**
现在两边都调 `page_sql`。

### 3.86 只打印数字的基准，等于让人用肉眼当断言

这次回归是"我碰巧跑了一次基准、碰巧注意到 68.6ms 旁边的注释写着 9ms"才发现的。
下一次可能就没人注意。

给关键指标加了预算（`BUDGET`），超了就 `exit 1` 并点名。**门槛设得比实测宽得多**
（9ms 的指标给 25ms），因为它要抓的是"结构上出错了"——索引没用上是 7 倍，机器忙
不会是。加完照例反向验证：把预算调到 1ms，确认它真的会红。

### 3.87 清单里的数字，必须和它随行的那份数据出自同一时刻

整库导出的 manifest 写着 101452 条，而压缩包里的数据库有 101476 条。两个都没算错——
条目数是另查**活库**得来的，而数据库是那之前一瞬的快照，中间又写进去二十几条。

**一份和身边数据对不上的清单，比没有清单更糟**：它会让接收方相信一个错的数字，
而且没人知道该信哪个。改成从快照文件本身数。

这和 3.69「两边数的不是同一样东西」是同一条，只是这次两边差的是**时间**而不是口径。
凡是"描述某份数据"的元信息，都要从那份数据里取。

### 3.88 顺手加依赖之前，先看这件事属于哪一层

为了数快照里的条目数，我在 yk-server 里直接用了 `rusqlite`——编译不过才发现它在这个
crate 里只是 dev 依赖。**这不是障碍，是提示**：yk-server 一直经由 yk-store 访问数据库，
直接开 SQLite 会把数据库处理散到两个地方。

助手函数放进了 yk-store（拥有 SQLite 的那一层）。规矩：**编译器说"这里没有这个依赖"时，
先问"这段代码是不是放错了地方"，再考虑加依赖。**

### 3.89 只导得出、导不回来，那不是门，是个洞

上一轮做完整库导出就该接着做导入。**一个没有程序能读回来的文件，不叫数据可携。**
所以这一轮补上，并且冒烟里的证明不是"接口返回 200"，而是：
造一个标记条目 → 导出 → **永久删除它** → 导入归档 → 它按**原 key**回来了，
其余全部计为 skipped，failed 为 0。

设计上选**合并而非替换**：目标库是空的（新机器）时合并就是还原；目标库非空时，
替换会毁掉没人问过的工作。已存在的（按 key）原样保留。

### 3.90 解压别人给的 zip，成员名可以是 `../../.ssh/authorized_keys`

这是 zip 格式最老的陷阱：把成员名直接拼到目标路径上，就等于让对方决定往哪写。
`zip` crate 的 `enclosed_name()` 返回 `None` 表示"这个名字会逃出去"，据此跳过即可。
配了一条测试：造一个含 `../escaped.txt` 的压缩包，断言**它没被写到暂存目录外面**，
同时合法成员照常解出。

规矩：**凡是外部来的归档/路径，先问"它能不能指到我不想让它指的地方"**，
并且用一条会真的写出文件的测试来证明它不能。

### 3.91 导入要保住 key，否则链接全断而外表毫无异样

条目的 key 是父子关系、收藏夹、引文共同指向的东西。导入时重新生成 key，
**条目本身看起来一条不少、字段全对**，但附件不再属于任何论文、收藏夹空了、
引文指向不存在的条目——而且没有任何报错。

`ItemDraft::key` 就是给导入用的（Zotero 导入也走这条路）。顺带一提：**version 不能带过来**，
它属于条目将要进入的那个库，不属于它离开的那个。

### 3.92 长任务不该占着 HTTP 请求

重建索引 29 秒、导出 9 秒、导入可能几分钟。把这些做成"等着请求返回"，代价是三样：
客户端整段时间没有东西可显示、反向代理有权超时、用户一刷新就再也找不到那件事。

改成"请求负责启动，返回一个句柄"：`POST` 返回 task，`GET /tasks/{id}` 看进度，
`POST /tasks/{id}/cancel` 请求停止。**取消是任务在步骤之间自己检查的标志，不是杀线程**——
导入在**页与页之间**停，而不是半页中间，因为后者会留下没人选择过的中间状态
（合并语义让"已经写进去的"恰好等于下次重试会跳过的，所以停在这里是安全的）。

刻意**没有**和 agent 的 `runs` 合并：一次 turn 是每个会话一个、带 transcript、
往事件总线推流；一个 task 是可以有很多个、带结果、被轮询。**它们相似的时间，
只有写到第二个之前那么久。**

两个具体的判断：
- **`total = 0` 表示"数不出来"**，前端据此显示转圈而不是编一个百分比。
  **会被相信的假进度条，比转圈更糟。**
- **已结束的任务要保留一段时间**（这里 50 个），否则刷新过页面的客户端再也拿不到结果；
  修剪要在**任务结束时**做，因为那才是数量增长的时刻——只在启动时修剪，
  边界会变成"上次启动以来结束的都还在"，一句话说不清楚。

### 3.93 轮询循环只写一次

三个页面各写一遍"每秒查一次直到结束"，就是三次机会忘记停下来。抽成 `lib/tasks.ts`
的 `follow()`：任务消失（已被修剪）返回 `null` 而不是死循环，**失败作为结果返回而不是抛异常**
——调用方要说的是"哪里出错了"，一个被 reject 的 promise 只会让这件事更难写。

### 3.94 "请求它停"和"它停了"是两件事

任务注册表最初这样判定结束状态：`finish()` 时看一眼取消标志，置位就记为 Cancelled。
看着合理，实则**会撒谎**——重建索引根本不检查那个标志，它会一路跑完；但只要有人点过
停止，结果就被记成"已取消"，而工作其实全做完了。

改成由**任务自己说**：`finish()` 永远是 Done，提前停下来的任务调 `stopped()`，
并带上它已经完成的部分（"导入到第 400 条停了"这件事里，那 400 条是真的）。

规矩：**状态机里的每个终态，都要由知道真相的那一方写入。** 注册表看得见的是
"有人按了按钮"，看不见"按钮起没起作用"——用前者推断后者，就是用愿望代替事实。

### 3.95 接口改了形状，先去找断言它旧形状的测试

`reindex` 从"返回 `{reindexed: n}`"变成"返回一个 task"，API 测试当场红了——
**这正是它该做的**，而且这次红得很便宜（`left: Null, right: 1`，一眼就知道是形状变了）。

值得记的是另一面：冒烟里**根本没有** reindex 的检查（它要 29 秒）。如果那条 API 测试
也不存在，这次改动就会悄悄发布一个没人调用得通的接口。**慢到不适合冒烟的东西，
更要有一条快的集成测试守着**——否则它就是完全没被测过。

### 3.96 搬走一套机制时，先清点它顺手守着的规矩

把引文抓取从"自带一套 `Harvest` 状态 + 起停接口 + 自己的轮询"迁到任务注册表上，
功能一条没少——**但"同一时间只允许一次"的守卫掉了**。它原本藏在
`if harvest.running { return Err(...) }` 里，看起来只是个状态检查；实际上它拦的是
"两个抓取同时打同一个 Crossref、把客户端搞到限流"。

是冒烟里那条 `harvest one only` 把它捞回来的——**那条检查的注释写着它为什么存在**，
所以看到它红，一眼就知道丢的是什么。

规矩：**删掉一段状态管理之前，先把它顺带执行的每条规则列出来。** 它们通常没有名字，
就长在 `if` 里；迁移会保住"功能"，而这些规则不算功能。新家里要重新给它们一个位置
（这里是 `Tasks::running(kind)` ——注册表本来就是唯一知道"什么在跑"的地方）。

### 3.97 泛化要等第二个真实使用者

任务状态一开始只有 `done` / `total`。抓取需要"存了多少条引文、多少家出版商没存"——
这些数字对导出毫无意义。塞进 `message` 字符串会逼界面去解析英文来画表格。

于是加了 `detail: Option<Value>`，由任务自己填。**这是被第二个真实使用者驱动的扩展**：
如果在只有导出的时候就先设计一个"通用扩展字段"，那是猜；现在有两个形状不同的任务
摆在面前，边界才是量出来的。

### 3.98 "database is locked" 未必是锁，可能是连接池被占满

把导入改成后台任务之后，冒烟里两条**用到模型**的检查开始失败，日志是
`database is locked`，请求整整等了 15 秒（正好是 `busy_timeout`）。

第一反应是"并发拷贝整库把库锁住了"。**去复现，没复现出来**：在备份和整库导出同时
进行时连续写入，全部 200，最慢 79ms。

真凶是归档导入里的 `for item in page { store.items.get(...) }`——十万条目就是十万次
往返，几乎持续占着池里的连接。**库一点没被锁，是池子没有空闲连接**，
而这两件事从错误信息里看起来一模一样。

改成一页一次 `get_many` + 一次 `create_many` 之后，冒烟全过，日志里
`database is locked` 出现 **0 次**。

规矩：**看到"锁"先问"是谁在等谁"**，并且先复现再修。另外，"每条一次查询"这种写法在
同步接口里只是慢，改成后台常驻之后会变成**别人的故障**——因为它现在和所有请求抢池子。

### 3.99 接口改形状时，测试的重复调用要先收拢成一处

Zotero 导入从"同步返回结果"变成"返回任务"，API 测试里有**五处**在读旧形状。
逐处打补丁改到第三处就开始手滑（漏了两个调用点，跑两轮才发现）。

正确顺序是：先在测试文件里加一个 `await_task(path, body)`，把五处都改成调它，
以后再变形状就只改一处。**测试代码同样适用 DRY——尤其是它正因为不 DRY 而正在变红的时候。**

### 3.100 上一条教训学会之后，要顺手把同族的地方都扫一遍

3.98 里"逐条查询在后台会变成别人的故障"是从归档导入学到的。学到之后**在全仓
搜同一形状**（循环体里 `await` 一次 store 调用），又找到两处：

- `graph::titles_for`：每个图节点一次 `get`，几十次往返换一张图的标签。
- `files::forget_files`：**清空回收站**时每个条目一次 `children` 查询，再逐个删目录。
  这是最坏的一处——它在删除请求内部，而"全选清空"会把整个库过一遍。

前者换成 `get_many`；后者需要一个新的批量接口 `children_of`（一条 `parent_id IN (…)`），
外加把文件删除合并成一次 `spawn_blocking`（同 3.60）。

规矩：**每条教训都要当成一次搜索条件用掉。** 只修发现它的那一处，等于把同样的
故障留给下一个人重新发现一遍。

顺带一条：给新的批量接口配的第一条测试是**超过 SQLite 变量上限**（4 万个父条目），
因为"全选然后清空回收站"正是会踩到它的手势——这个坑在这个仓库里已经踩过两次了。

### 3.101 基准数字变差之前，先确认基线也变差了

图谱邻域这次量到 47.8ms，而文档里记的是 ~18ms，看起来像我刚做的改动搞坏了。
**把改动 stash 掉重测：45.1ms。** 早先那个 18ms 来自语料更小、引文更少的时候。

规矩：**"比记录的数字差"不等于"这次改差了"**。语料会长，基线会漂；怀疑自己之前，
先花两分钟测一次没有改动的版本。反过来也一样——别把语料变小带来的提速记成功劳。

### 3.102 不像真实库的语料，既会藏起缺陷，也会凭空造出缺陷

3.54 记的是"语料不真实就看不见真实缺陷"。这次是反面：**图谱邻域 45ms**，看着像个
待优化的慢查询，追下去发现是夹具的问题。

基准给每个条目挂两个标签，取自三十来个宽泛词。于是一个标签动辄覆盖上万条，
"共享这个标签的论文"就横跨半个库——图谱的标签重叠聚合因此要算几万行。
真实的标注是长尾的：少数几个词铺得很广，大量项目专用的标签各自只有两三条，
而这正是"共享标签"能成为一个**小集合**的原因，也是这个功能存在的前提。

把语料改成长尾分布之后，同一份代码：**图谱 45ms → 5.1ms**。一行代码没改。

规矩：**看到一个慢数字，先问"真实的库会长这样吗"**，再问"代码怎么写快一点"。
否则就会为一个不存在的场景做优化——而优化通常意味着复杂度，那份复杂度会永远留下来。

排查过程里的两个方法论点，都值得记：
- **"无向量的条目图谱只要 6.5ms"曾让我认定瓶颈是向量检索**，其实那个条目只是恰好
  很稀疏。**对照实验只改一个变量**：真正的答案来自把 `similar` 那一行临时删掉再测
  （45ms → 37.6ms，向量只占 8ms）。
- 又一次差点测错服务器：`--port 23150` 上早有别的实例，我的进程 `Address already in use`
  直接退出，而基准照样连上了**别人的库**并报出 10 万条目。**启动服务后要验证它确实是你启动的那个**
  （`ping` 回报的 `dataDir` 是最直接的证据）。

### 3.103 把同步任务改成后台任务，等于第一次把它和整个程序放在一起跑

`reindex` 做了十几轮同步接口都没出过问题——因为**调用方在等它，没有别人在写**。
改成后台任务的当天，冒烟里两条无关的检查开始报 `database is locked`，等满 15 秒。

拆下来是一条完整的链，每一环都只有在并发下才存在：

1. **清空索引是一个事务**：从两张 FTS 表和向量表里删掉十万行，独占写锁 18 秒。
   → 按 id 分批。
2. **分批但不让步，仍然会饿死**——而且这次饿死的是**它自己**：重建反复抢不到锁，
   耗尽 busy timeout 直接失败。→ 每批之间 `yield_now()`（嵌入工作线程早就这么写了，
   注释里还写着"an earlier version did exactly that"——**同一课上了两次**）。
3. **重建造出巨大的 WAL，WAL 招来 `wal_checkpoint(TRUNCATE)`，而 TRUNCATE 要独占整个库。**
   这才是最后那 15 秒的真凶。→ 重建期间不做 truncate 检查点：日志大几分钟，
   总好过程序几分钟不接受输入。
4. 每一批都是幂等的，所以**抢不到锁应该是"等一下"而不是"放弃半个索引"** → 有界重试。

修完：重建进行中连续写入 20 次，**0 失败**，重建也正常完成。

规矩：**"它一直好好的"只说明它一直没和别人同时跑。** 任何长任务从"调用方等待"改成
"后台运行"，都要重新回答三个问题：它一次占锁多久、它让不让别人插队、它被别人挤掉时会怎样。

### 3.104 让"启动服务"这件事自己验证自己

`setsid … &` 在端口被占时**返回成功**：新进程写下 `Address already in use` 就退出，
旧进程继续应答，于是基准/冒烟测的是另一个库。这个坑已经付过三次代价（§3.52、§3.55、§3.102）。

`scripts/serve.sh` 现在做三件事：端口被占时**报出占用者正在服务哪个库**并拒绝
（除非 `--replace`）、等待 `/ping`、**核对 `dataDir` 确实是你要的那个**。
基准和冒烟也都接受 `YK_DATA`，不匹配就拒绝运行而不是照跑。

规矩：**凡是"启动某个东西然后对它做事"的脚本，都要有一步回答"我在对谁做事"。**

### 3.105 修好一个任务之后，同一批迁移的其它任务也要挨个量一遍

上一轮修的是 `reindex`。**同一批还改成后台的导入任务，我一个都没测过。**
按 3.103 的三个问题挨个量：

- 归档导入（跳过路径）：写入 2–3ms，没问题——**但这个测试是假的**，条目都已存在，
  几乎没发生写入。换成导入**空库**（10.2 万条真实写入）才是真的测试。
- 空库导入：0 失败，但最慢 833ms。

规矩：**"我测过了"要先问"我测到那条路径了吗"。** 一个批量写入的任务，用一份
全是重复条目的输入去测，测的是 `get_many` 不是 `create_many`。

### 3.106 `yield_now()` 治不了 SQLite 的锁争用

看到导入期间写入要 800ms，顺手在批次之间加了 `yield_now()`——**复测最慢反而 2.6 秒**。
它让出的是 tokio 的调度权，而争用发生在 SQLite 的单写锁上；让出调度只是让本任务的
下一次 `call` 稍晚派发，别人未必就抢得到。

真凶还是 checkpoint：上一轮我只把 truncate 检查点对 `reindex` 关掉了，
而**规则应该是"任何批量写入运行期间都不要独占数据库"**。推广之后：
**最慢写入 2.6s → 232ms**。

两条规矩：
- **没有测量支持的"优化"要删掉，哪怕它看起来无害。** 那两行 `yield_now` 已经撤回——
  留着就是给后人一个"这里已经处理过了"的错误印象。
- **修一个具体案例时，先写出它的一般规则再落地。**"重建期间不 checkpoint"是案例，
  "批量写入期间不独占"才是规则；只修案例，下一个任务会再踩一次。

### 3.107 并发测试要先证明自己真的并发了

前三轮的并发结论全是手动 curl 测出来的——**手动测出来的性质，也会用手动的方式丢掉**。
写成集成测试：建库、启动重建、边跑边写、断言写入全部成功。

第一版 1.08 秒通过，**而它几乎什么都没测**：加一条"这次写入发生时重建还在跑吗"的计数
之后才发现，25 次里只有 3 次真的重叠——重建早就结束了。

规矩：**任何"A 运行期间 B 仍然正常"的测试，都必须断言 A 当时确实在运行。**
否则它会永远是绿的，而绿的原因是两件事根本没碰上。

同样重要的是**别断言你量不准的东西**：把缺陷放回去，最慢写入 106ms vs 修复后 69ms，
这个差距撑不起一条阈值断言（测试规模下清空 8000 行本来就快）。真正的差距在生产规模
——232ms 对上"等满 15 秒然后失败"。所以测试里那行延迟只打印不断言，
并在注释里写明为什么、以及真实数字在哪一节。

失败信息也要写准：`overlapped` 不足有两种解释（任务结束太早／写入被堵到任务都结束了），
两种都说明性质没被证明，而不只是"测试没测到"。

### 3.108 把工作挪到后台，就欠用户一个"它去哪了"的地方

任务系统做完之后，功能上没问题：接口立刻返回、进度可查、可取消、状态栏有转圈。
**但用户一小时后想问的是"我导出的那个文件叫什么、在哪"**——而那句话只出现在
一个早就消失的 toast 里。

补了 Jobs 标签页：做了什么、到哪一步、怎么结束的、产出是什么。
其中"产出"这一列是有讲究的：**每类任务的结果形状不同，有用的部分也不同**
（导出是一个要去找的文件名，导入是新增/已存在的条数）。把这份知识集中在一个
`outcome()` 里读，而不是让每个任务自己拼一句英文——那样界面就再也翻译不回去了，
也就没法做 i18n。

规矩：**异步化一个操作，同时要回答"结果留在哪里"。** 通知是事件，而结果是状态；
把状态只放进一次性通知里，等于让用户去记住它。

### 3.109 有统计信息的库和刚建好的库，是两个不同的查询规划器

重建基准语料之后，同一个接口在新库上 19–26ms，在旧库上 5.6ms，返回的
payload 几乎一样大（60KB / 62KB）。逐段量过：页查询 0.27ms、count 4ms、
标签 hydrate 0.25ms、WAL 3.1MB、重启进程无效——差值不在任何一段里。

唯一能复现的线索是：`ANALYZE` 之前这个语料量到 8.3ms，跑过
`PRAGMA optimize` 之后变成 22ms 并稳定在那里。也就是说，**统计信息改变了
接口路径上某个不是页查询、不是 count、也不是标签 hydrate 的计划**，剩下
的嫌疑是 hydrate 的另外两趟（collection、附件标记）和 badge/plugin 路径。
这一条没查到底，如实记在这里，不要因为"没查明白"就顺手把预算调大——
预算是用来发现这种事的，不是用来消化它的。

能确定的结论有一条，已经落到 `scripts/bench.mjs`：**播种完要先
`optimize` 再测量**。真实用户的库跑过 `PRAGMA optimize`，刚 seed 出来的
没有；不补上这一步，就是拿一个规划器的数字去和另一个比。补上之后
collection 分页从 22.6ms 掉到 14.6ms，代码一行没动。

### 3.12 别的教训（散落在各处，集中记在这里）

- **迁移必须按名字应用，不能按位置。** 撤销过的迁移会永久占用它的编号；
  接替那个编号的迁移在见过前者的库上永远不会执行。见 `db.rs`。
- **离线性能探针必须先设上生产 PRAGMA**（64 MiB 页缓存 + mmap），
  否则测出来的加速比是探针的，不是用户的。见 `docs/15` 第 6 节。
- **聚合里的每一样东西都要付 N 次。** 谓词放在聚合内还是聚合外，可以差两个
  数量级以上。见 `docs/13` 末节。
- **前台 checkpoint 会让某次写入付出整份 WAL 的代价**（p95 是 p50 的一百倍）。
  `wal_autocheckpoint = 0`，交给后台 worker。见 `db.rs`。
- **`check` 这类"非空即通过"的断言，必须让错误答案为空**，否则错的字符串也算通过。

### 3.110 客户端不在类型系统里，就得有一条测试把名字钉住

Word 任务窗格是纯脚本，从二进制里发出去，不经过本仓库任何类型检查。
第一版写的是 `plan.updated`；服务端序列化出去的字段叫 `updatedFields`。
在 JavaScript 里读一个不存在的属性不是错误，所以症状会是：窗格能插入引文，
然后每一条都是空的，**任何地方都不报错**。

这个 bug 不是读代码发现的，是**照着窗格的调用顺序，对着真服务器重放一遍协议**
发现的——建条目、开会话、按文档顺序发两个域、再发一个"粘贴进来的空域"。
一次 curl 会话就把两件事都量出来了：字段名错了，以及空 keys 的域会被服务端
从 `updatedFields` 里剔除（于是文档里那条保持原样，这是对的）。

已经落成 `tests/wire_names.rs::the_word_pane_reads_names_the_server_actually_sends`：
序列化一个 `Plan`，扫描 `taskpane.js` 里所有 `plan.<name>`，逐个比对。
写这条测试时又抓出第二个问题：`insertBibliography` 里也有个变量叫 `plan`，
装的却是 `/bibliography` 的另一种形状（`{html, entries}`）。
**一个变量名指两种形状，正是 `plan.updated` 被写出来的原因**——已改名。

扫描要跳过整行注释：文件里正好用散文解释了这个错误，而一条分不清"说明"和
"指令"的守卫，人们很快就学会把它关掉。

### 3.114 "在文件管理器中显示"不需要外壳程序，但需要两条铁律

server 本来就在用户机器上，直接起文件管理器即可。安全性全靠两条：

1. **客户端只给 key，绝不给路径。** 路径由服务端按自己的存储布局解析。
   一个 `path` 参数会把这个端点变成"远程打开磁盘任意文件"，而浏览器里
   任何一个页面都够得着它。
2. **全程不经 shell。** `command()` 返回程序名 + argv 数组，直接交给
   `Command`；文件名里的 `;`、`$(…)` 没有任何地方会被解释。已有一条测试
   专门断言这件事（`a_hostile_filename_stays_one_argument`）。

把"选哪个程序、给什么参数"做成**纯函数**，是这个模块唯一能被测的办法——
真正的 spawn 在 CI 里既跑不动也看不见。于是三个平台的调用约定都有测试：
Windows 的 `/select,<path>` 必须是**一个**参数（拆开会静默打开"文档"目录），
macOS 少了 `-R` 就变成用 Preview 打开（看起来也像成功了），
Linux 对文件用 `xdg-open` 是*打开*而不是*显示*，得走 `FileManager1.ShowItems`。

无桌面会话时**如实报错**。两种情况下屏幕上都什么都不发生，回 ok 是用户
无从分辨的谎。

### 3.115 不是所有能力都得由服务端长出来

缩略图的显然做法是"服务端渲染 PDF 页"，那意味着 pdfium 或 mupdf：一个按平台
分别构建的大型原生依赖，而这个程序的全部前提是"用户装得上"。

但**浏览器里已经有 pdf.js，而且刚刚就把那一页画出来过**。于是分工反过来：
客户端渲染，服务端只做缓存。`GET` 未命中时返回的 404 **就是协议本身**——它在
告诉客户端"画一张，PUT 回来"。整个功能没有增加一个依赖。

判断标准不是"这个能力属于谁"，而是"谁手上已经有做这件事的东西"。

配套的两条限制，缺一个缓存就不再是缓存：
- **宽度取自固定集合，不接受区间。** 每个不同宽度都是磁盘上一个文件；区间等于
  让一个调用者从 240 往上数着把缓存塞满。
- **按魔数校验字节是不是图片。** "客户端上传、我们存下来、再从用户自己的源上
  发回去"，否则就是一条在用户源上托管任意内容的路径。调用者给的
  `Content-Type` 是一句断言，不值钱。

### 3.116 跨语言的常量必须有一条测试把两边钉在一起

宽度列表同时存在于 Rust（`WIDTHS`）和 TypeScript（`THUMB_WIDTHS`），
两个编译器谁也看不见谁。一旦漂移，客户端会去要一个服务端拒绝的宽度，
**封面就静默地不再出现**，而唯一的线索是一个没人开着的网络面板里的 422。

第一版我在 TS 里写了个"断言常量等于 [96,240,480]"的测试——那只是把常量抄了
一遍，没有守住任何东西。真正的守卫是**从一侧读另一侧的源文件**，照
`wire_names.rs` 的老办法：Rust 测试 `include_str!` 那个 .ts 文件，逐个断言
`WIDTHS` 里的数字都出现在客户端的声明行里。

判据：一条测试如果在两边同时改错时仍然通过，它守的就不是那个契约。

### 3.117 同一个过滤条件，两种写法，两个数量级——而且方向相反

`list filtered by tag` 长期是浏览类里最慢的一项（36ms，其余 8ms）。原因不是索引
缺失，是**同一个语义有两种 SQL 写法，各自在相反的场景下快**：

| 标签命中数 | `IN (SELECT ...)` 物化后排序 | `EXISTS (... item_id = i.id)` 顺序扫描 |
|---|---|---|
| 4 | **0.1ms** | 50.2ms |
| 4,587 | 8.2ms | **0.8ms** |
| 28,709 | 33.2ms | **0.2ms** |

物化写法要收集全部命中行再用临时 B-tree 排序（只为取 100 行）；探测写法沿排序
索引走、够一页就停，但标签越稀有走得越远。**没有一种写法总是对的**，所以
filter.rs 里那条"`IN` 比 `EXISTS` 快 3.4 倍"的老注释只是记录了当时那一个样本。

代价模型给出精确判据：物化 ≈ `total`，探测 ≈ `rows × window / total`，
两者相等即 **`total > sqrt(rows × window)`**。131k 库、100 条一页，交叉点约 3620，
与上表实测吻合。

`rows`（库存量）从 **`sqlite_stat1`** 读，0.005ms；真去 `count(*)` 要 5.8ms,
比它要决定的那个查询还贵。**估计值正是这里需要的精度**——判据两侧差着数量级，
差几个百分点不可能改变答案。没有统计信息时返回 0，规则退回旧计划：没人 ANALYZE
过的库，安全选择是那个不会变坏的。

结果 36.2ms → 17.3ms，且剩下的几乎全是 count（页查询已降到 ~0.2ms）。

**这类优化必须先证明选择是不可见的。** `tag_form_equivalence` 拿同一个库把两种
写法逐页对比：常见标签、稀有标签、根本不存在的标签、两个标签，以及每一种排序。
不存在的标签尤其要测——内层标量子查询返回 NULL，而 NULL 在 `IN` 和 `=` 里行为
不同，两边都必须是"没有行"而不是"所有行"。速度是次要的，**有没有资格选**才是
前提。

### 3.118 "先全取，再过滤掉不要的"——这行代码永远值得看第二眼

改名预览 314ms，是整份基准里最大的绝对数字。原因在 `plan()` 的两行：

```rust
let page = items.attachments(lib, u32::MAX, 0).await?;   // 整库三万个附件
for (attachment, parent) in page.items {
    if !chosen.is_empty() && !chosen.contains(&attachment.key) { continue; }
```

用户选中 12 个文件要改名，程序读出三万行，然后**每行对选中列表做一次线性扫描**
把 29,988 行扔掉——选得越多越慢，正好和直觉相反。改成"选中时按 key 批量取"
之后：**313.7ms → 1.5ms**（12 个），100 个时 271ms → 4.1ms。

整库改名那条路径没有变快，也不该变快：规划整个库本来就得读整个库。
**分清"这个操作固有的代价"和"这份实现附加的代价"**，只优化后者。

配套教训：`scripts/bench.mjs` 只测了整库那条路径，也就是**唯一没被改动的那条**。
改进的路径一开始无人看守。现在两条都在测，选择路径有 15ms 预算。
写基准时问一句：**我测的是用户真正走的那条路吗？**

顺带（DRY）：`measure()` 把"打印 + 预算检查"揉在自己体内，于是 POST 类的测量只能
自己拼格式串输出——而自己拼格式串的测量是没有预算守着的。已抽出 `report()`。

### 3.119 单词查询的"回退"是同一条语句

`lexical::keyword()` 先跑合取、无果再跑析取。但一个词的查询，
`parts.join(" AND ")` 和 `parts.join(" OR ")` 得到的是**同一个字符串**——
于是任何单词且无命中的查询，会把同一条 FTS 语句原样跑两遍。代价恰好落在
已经什么都没找到的那些查询上。

现在记住上一次跑过的表达式，相同就跳过。测试直接断言
`match_expression("transformer", true) == match_expression("transformer", false)`，
把这个前提写在明处，而不是留给下一个读代码的人自己发现。

### 3.120 判据只问"是否超过阈值"，那就只数到阈值

§3.117 用 `total > sqrt(rows × window)` 选计划，那里 `total` 是白拿的——
`items::list` 本来就要算 count。但搜索引擎里没有这个数：`tag:survey` 走
`matching_ids`，而它压根不算 count。

于是有了一个更好的形状：**规则只问命中数是否*越过*交叉点，那就只数到交叉点为止。**

```sql
SELECT count(*) FROM (SELECT 1 FROM item_tags WHERE tag_id = ? LIMIT ?)
```

代价 O(√(rows × window))，**按构造比它要在其中做选择的两种计划都便宜**：
131k 库上最坏 0.136ms，而它避开的那条查询是 44.5ms。这不是估计，是精确回答了
那个（也只有那个）被问到的问题。

只对单个正标签使用。两个 AND 标签的结果不大于任一集合，探测其中一个只是上界，
**而上界只会把"该走"判错**。

### 3.121 同一个上限用在两种含义上，必然对其中一种是错的

`allowed()` 一律取 20,000 个 id。但这些 id 有两种截然不同的用途：

- **有搜索词时**它是*限制集*，各路排序腿从全库出结果，命中可能落在任何位置，
  所以集合必须足够宽。
- **没有搜索词时**（`tag:survey`）它*就是答案本身*，按序排列，而调用方只要一页。

同一个 20,000 用在两处，于是 `tag:survey` 读了两万行来返回五十行。区分开之后
（`want = offset + limit + 1`），加上 §3.120 的计划选择，**32.5ms → 2.5ms**。

`+1` 不是随手加的：它让调用方分得清"这是最后一页"和"后面还有"。而这个上界
恰恰是最容易把分页写坏的地方，所以测试直接翻完三页、断言没有重叠也没有缺口。

顺带把 `estimated_items` 从 `items.rs` 挪进 `filter.rs`——规则和它需要的输入
应该在同一个地方，否则第二个调用方只会再抄一份。

### 3.122 我自己两轮前埋的：`tags_only` 不等于"正在探测"

§3.117 加计划选择时，我顺手把 `page_sql` 的索引提示条件从 `base_only` 扩成
`base_only || tags_only`——理由写得也像那么回事："探测形式也要靠这个索引才能
够一页就停"。

错在 `tags_only` 描述的是**过滤器的形状**，而提示要匹配的是**这次实际选了哪种
写法**。稀有标签会选物化写法，却照样被按上 `INDEXED BY idx_items_modified`，
于是 SQLite 不再从标签驱动、改为扫整条索引：

```
materialise, no hint            0.1ms
materialise + INDEXED BY       13.1ms      ← 131 倍
```

修法是让谓词自己记住 `probing: bool`，`index_hint()` 只在 `base_only || probing`
时给出提示。同时把"选哪种写法"收进 `Predicate::for_page()` ——
**两个调用方各自做同一个决定，长出了两个略有差异的版本，而第二个是错的。**

### 3.123 一个二选一的决定，两侧都要有人看着

基准里只有 `tag=survey`（28,727 条）。整个 §3.122 的劣化就发生在另一侧，
所以三轮之内没人发现——**基准盯着的是这个决定的一半**。

现在加了 `list filtered by rare tag`。第一版写死 `tag=project-1`，结果 `n=0`：
那个标签在这个语料里根本不存在，这条测量量的是空结果——**一条为了错误的理由
而通过的检查**（同 §3.55 的老毛病）。改成从 `facets` 里挑出计数最小的标签，
并把选中的名字和计数打印出来。

规律：**凡是"根据 X 选 A 或 B"的代码，基准里必须同时有会选 A 的用例和会选 B 的
用例**，否则被优化的那一侧越快，另一侧越没人管。

### 3.124 一次浏览的时间，大半花在数数上

翻页取一百行是从索引里读一百行；**算总数要走遍每一个命中**。
131k 库上：纯浏览 8.3ms 里 5.8ms 是 count，标签过滤 17.8ms 里 13ms 是 count。
而滚动列表时，每一页都在把同一个数重算一遍。

`counts.rs` 按 **(库 id, 谓词 SQL, 绑定参数, 库版本)** 缓存这个数：

| | 之前 | 之后 |
|---|---|---|
| list first page | 8.3ms | **4.4ms** |
| list deep page | 8.8ms | **5.0ms** |
| list sorted by title | 8.6ms | **4.5ms** |
| list filtered by tag | 17.8ms | **4.4ms** |

**这里没有任何陈旧数据**，和 `cache.rs` 是不同的交易。`cache.rs` 明确用一瞬间的
精确性换掉一次卡顿（并且只在重算确实慢时才换）；而 total 决定客户端认为有多少页，
一个和身边行数对不上的总数不值那几毫秒。键里带着库版本，任何写入都会让它变化，
所以命中的要么正是被查询的那个状态，要么就不用。读版本号 0.0072ms，未命中几乎
不为"看了一眼"付钱。

整个缓存立在一条性质上：**任何能改变计数的写入都必须提升库版本**。
`tests/count_cache.rs` 就测这个，而且专挑不显然的：给条目加标签，改变的是每个
标签过滤器会报的数；加入收藏夹，改变的是那个收藏夹的数。

容量满了直接清空而不做 LRU——维护一个最近使用顺序比被缓存的东西还贵，
清空的代价只是接下来几次请求付回它们本来就要付的钱。

### 3.125 预算贴着测量值会因为机器忙而失败，不是因为代码坏

count 缓存把浏览从 8.3ms 降到 4.4ms 之后，很想把预算从 25 收到 6 来"守住"它。
不能这么做：这些数字的职责是抓住**计划坍塌**（索引没被命名时 9ms → 69ms），
而贴着测量值的阈值只会先因为机器忙而失败，然后被人调大或者关掉。

收到 15：仍有三倍余量，仍能抓住任何量级上的退化。守住缓存本身要靠
`tests/count_cache.rs` 的正确性测试，不是靠掐秒表。

### 3.126 基准问错了参数，就会替产品背一个不属于它的数字

`facets` 的 p99 一直是 230ms，看着像侧栏会卡。查下去才发现：
**服务端启动时已经预热了 facet 缓存，前端也刻意不发 `limit`（好命中那个槽），
而基准发的是 `?limit=60`** —— 一个没人预热、也没人请求的槽。

于是基准第一次调用付 232ms 冷成本、之后 1.9ms（它自己把自己的槽热了），
报出来的数字和用户实际体验差三个数量级。更糟的是：**预热逻辑因此完全没有覆盖**，
它哪天坏了，基准上一个数字都不会动。

这是同一个形状第三次咬人（见 §3.48、§3.49）。规则说得再直白些：
**任何带缓存的端点，基准必须原样发送客户端发送的参数**——不是"差不多的"，
是同一个。多一个 `limit` 就是另一个缓存键。

改对之后 p99 232ms → 2.0ms，代码一行没动。

顺带补上预热的守卫：`measure()` 现在把**第一个样本**也带回来。基准跑起来时
启动早已结束，所以第一次调用是热的——*前提是预热确实做对了*，而这是唯一
能说明问题的样本；另外 39 次会互相热身，中位数什么都看不出来。
实测未预热的槽是 220ms，阈值 40ms，足够分辨。

### 3.127 同一个问题的两种问法，只有一种走了缓存

上一轮给 `list` 的总数加了缓存，`items.count()` 却还是原样重算——
两处各自建谓词、跑同一条 count SQL。于是 `/stats` 在每次工作台加载时
把整个库重数一遍。

抽成一个 `cached_count()`，两个调用方共用。加上把 `/stats` 里六个互不依赖的
查询从串行 await 改成一个 `tokio::join!`（答案的耗时从"全部之和"变成"最慢的那个"），
**10.9ms → 6.7ms**。

`tests/count_cache.rs::count_and_list_never_disagree` 钉住这件事：它们是同一个
问题的两种问法，一旦又变成两份实现，就会有一份忘记跟上。

剩下的 5.36ms 是 `SELECT count(*) FROM items WHERE deleted = 0`——131k 行覆盖
索引扫描，约 40ns/行，已经到底。它跨库，因此库版本号这个失效水位线不适用；
**为一个诊断数字去造一个跨库水位线，风险大于收益**，就此打住并记录理由。

### 3.128 缓存放在一个仓储里，就只有那个仓储受益

上一轮把"活跃条目有多少"的计数缓存放进了 `SqliteItemRepository`。
这一轮发现 `graph.rs::common_tag_ceiling` 在算"标签常见到什么程度算噪音"时，
**每次画图都把整个库重数一遍**——同一个数字的第三个调用方，而它在另一个仓储里，
够不着那个缓存。

缓存提到 `Store` 层创建一次、注入两个仓储。加上把 graph 端点里五个互不依赖的
查询（`items.get` / `neighbours` / `similar` / `cites` / `cited_by`）改成一个
`tokio::join!`：**47.7ms → 28.8ms**。

判断依据不是"这个缓存属于谁"，而是**"这个问题有几个提问者"**。
计数被三处问到（列表的总数、`/stats`、图谱的天花板），它就该在三处都够得着的
地方。

### 3.129 断言写反了，但测试没白写

给上面这条写测试时我断言"库变大后邻居只多不少"，结果 `before 8, after 0`。
第一反应是缓存坏了，实际是**测试对了、断言错了**：天花板本来就是活跃条目数的
一个份额，覆盖全库的标签在库够大之后就该被判为噪音、不再连边。

而这恰恰是最好的可观测证据：**只有读到了新的总数，天花板才可能翻过去。**
改成断言这个开关本身——小库里共享标签仍然连边，大库里不再连——比原来那条
"只多不少"强得多，因为它会因为缓存陈旧而失败。

失败的测试先别急着改代码：**先确认失败的是断言还是被测对象。**

### 3.130 数完第四个提问者

按 §3.128 的视角（"这个问题有几个提问者"）把 `count(*) FROM items` 全库搜了一遍，
又找到两处手写的同一个问题：

- `items::attachments()` 自己数附件数 —— 1.54ms，文件浏览页和每次整库改名
  预览都付。
- `search::stats()` 数 `WHERE deleted = 0`（跨库）—— **5.36ms，占 `/stats` 的
  绝大部分**，而 `/stats` 是每次工作台加载都调的。

第一处直接换成 `cached_count` + `Predicate::build`，手写 SQL 消失。

第二处上一轮我搁置过，理由是"跨库，库版本这个失效水位线不适用"。缓存提到
`Store` 层之后有了干净解法：**跨库总数就是各库总数之和**（每个条目都属于某个库），
而每个分量都由该库自己的版本号守着，按构造正确。`/stats` **6.6ms → 0.7ms**，
数字和 `stats.items` 仍逐位相同（smoke 有这条断言）。

教训是上一轮那个"记录理由而不做"的判断本身是对的——当时确实没有干净解法；
**但这类判断要随着结构变化重新过一遍**，缓存换个位置，结论就变了。

### 3.131 一次浏览的开销现在都在别处

三轮下来（§3.117、3.120–3.121、3.124、3.127–3.128、3.130）：

| | 起点 | 现在 |
|---|---|---|
| list first page | 8.3ms | 4.1ms |
| list filtered by tag | 36.2ms | 4.5ms |
| tag operator | 32.5ms | 2.5ms |
| facets p99 | 232ms | 2.2ms |
| stats | 10.9ms | 2.0ms |
| graph neighbourhood | 47.7ms | 30.8ms |
| rename preview（选中 100 个） | 271ms | 4.8ms |

剩下最大的是搜索的 keyword 腿（"transformer" 命中 20,393 篇，27ms）。
那是 BM25 对每一篇命中文档打分的固有代价，逐条量过：`ORDER BY rank` 的
FTS5 专用路径不更快（31.5ms），去掉库作用域 join 也只省文档里写着的那 7ms。
**这一项不再是"还没优化"，而是"量过、到底了"**——别再重复排查它。

### 3.132 没被基准覆盖的端点，就是没人知道它慢

这一轮先量了载荷大小（都健康，59KB 压到 4.4KB），再量冷启动第一次请求——
结果在一个从来没进过基准的端点上撞见 **`/collections` 稳定 27ms**，冷热都一样。
它和 facets、stats 一起躺在侧栏首屏的 `Promise.all` 里，**首屏等的是最慢的那个**，
所以它一个人决定了首屏时间，比旁边几条慢十五倍，而三轮优化里没人看见它。

原因是 `C_SELECT` 里每个收藏夹一次的关联子查询在数"这个架子上有多少条活着的
条目"。改成一次分组连接：**26.8ms vs 27.1ms，没有区别**——SQLite 早就拍平了它，
代价是固有的（六万条成员关系，每条都要回 `items` 看 `deleted`）。
**先量再改，否则就会为一个不存在的问题写一版新 SQL。**

真正的出路是不重复做：按库版本缓存整个列表，27ms → 1.9ms，并加进启动预热
（连同 §3.126 的"只看第一个样本"守卫）。

`counts.rs` 顺势泛化成 `Versioned<T>`，`CountCache = Versioned<i64>`。
**缓存里有意思的从来不是值的形状，是失效的时机**；写第二份失效逻辑才是要避免的事。

值得记住的是这条列表由**条目**写入失效，而不只是收藏夹写入——每行都带一个活跃
条目计数。测试直接把这一点钉住：加入架子、扔进回收站、再改个名，三种写入都要
让列表跟着动。

### 3.133 把所有端点排队量一遍，找到的不止是慢

按 §3.132 的教训，这一轮把工作台会调的读端点全部计时。大部分在 1ms 以内，
两个例外，而顺着第二个还揪出一个功能 bug。

**`/duplicates` 191.8ms**（页面打开即加载，从未进过基准）——记下待办。

**`smart-collections?counts=true` 105.8ms**，就在侧栏首屏的 `Promise.all` 里。
我刚把旁边的 collections/facets/stats 都压到 2ms，它于是独占了首屏。原因是
每条保存的搜索都要跑一次完整搜索才拿到计数，而且是**逐条 await**。
并发化把冷路径压到 62ms，按库版本缓存把重复路径压到 0.6ms。

但真正重要的是量它之前必须先播种：**语料里一条智能收藏夹都没有**，
所以第一次测出来是 0.6ms——又一次"测了个空结果"（§3.123）。
`bench.mjs` 现在会播种五条保存的搜索，纯过滤和文本查询各有。

### 3.134 `total` 不能从 `hits.len()` 推出来，推了就是个功能 bug

播种智能收藏夹时顺手核对计数，发现 `/items?q=transformer&limit=1` 报 `total=1`,
`limit=50` 报 `total=50`——**`total` 一直等于当前页的行数**
（`views.len() + offset`）。

这不是显示不准而已。前端的无限滚动条件是：

```ts
if (s.loadingMore || s.loading || s.items.length >= s.total) return
```

于是**任何搜索都只能出一屏结果，再往下滚什么都不会加载**，而且不报错、
不空白，就是列表拒绝变长。两万篇命中里用户只能看到一百篇。

修法是让端口如实回答两个不同的问题：`SearchIndex::search` 现在返回
`SearchPage { hits, total }`，`total` 取融合后的候选数。它是"至少这么多"——
排序检索本就只给一个有界候选池打分，**说"至少"是诚实的，而且分页要的正是它**。

`hostapi` 里给插件的形状保持为数组不变：插件是被承诺过一个数组的，
把它拓宽成对象会打断每一个已经写好的插件。

教训不是"别写 `views.len()`"，而是：**两个不同的问题不要用一个字段回答**。
"这一页有几行"和"一共匹配了几条"从来不是一回事，把前者当后者用，
症状会出现在离它很远的地方（一个不肯加载的滚动列表），而且没有任何报错指向这里。

### 3.135 修好一个数字之后，要问它现在诚不诚实

§3.134 把搜索的 `total` 从"这一页的行数"改成了"融合出的候选数"。分页因此修好了。
但界面上那行字变成了"100 / 300"——而这个查询真正命中的是 **20,393** 篇。

300 正好是候选池上限。**排序检索本来就只给一个有界池打分**，所以那个数字是下界，
却被排版成了确数。改一个 bug 时很容易停在"不再是错的"，而不是"现在是对的"。

现在 `SearchPage` 多一个 `capped`：有任何一路检索恰好交回了它被允许的上限条数，
就说明它还有更多没给。`Page` 相应多一个 `approximate`（浏览是精确计数，不带这个
字段），界面据此显示 `100 / 300+`。

测试特意断言**两侧**：一个只有 12 条命中的搜索**不能**被标记——否则每次搜索都带
一个"+"，这个记号就不再有任何意义。

### 3.136 有些"慢"只是合成语料的形状

`/duplicates` 191.8ms，两条全库 GROUP BY。先试了给标题扫描指定索引：
**112ms → 145ms，更慢**；SQLite 自己选的 `idx_items_parent` 已经是最优。
所以只剩"不重复做"这条路——按库版本缓存，193ms → 6~8ms。

（合并会让缓存失效，但页面本来就只从本地列表里摘掉合并掉的那一组、不重扫，
所以这个缓存真正买到的是**切走标签页再切回来**——而标签页正是这个工作台的
主要交互方式。）

顺手量了载荷：**563KB**。剔掉页面不显示的摘要只省到 460KB，只保留真正渲染的
字段也还有 367KB——因为 22 个组里塞了 **806 条**。真实文献库里一组是两三条；
是播种脚本用小词表造出了成百上千个同名条目。**这一项到此为止，并记下原因**，
免得下一轮有人再来"优化"一个只存在于夹具里的问题（同 §3.102）。

### 3.137 注释里承诺的行为，不等于实现了的行为

`smart.rs` 里写着：

```rust
/// Counting a text query means running it; cap the work so a sidebar refresh
/// stays cheap. Anything at the cap is reported as "500+".
const COUNT_CAP: u32 = 500;
```

侧栏里渲染的是 `{sc.itemCount ?? ''}`——**从来没有那个 `+`**。而且注释还错了第二遍：
计数其实是被候选池（约 300）截断的，比 COUNT_CAP 更早。

顺着 §3.135 做诚实性审计时才发现的。教训：**读到"这里会显示 X"的注释，
就去看那一行是不是真的显示了 X。** 注释描述的是作者的意图，不是代码的行为。

### 3.138 "没有文本"不等于"能变成过滤器"

修上一条时我写了：解析之后 `parsed.text` 为空就走精确计数。
结果 `year:2020` 报出了**整个库**（131,701 条）。

原因：`ItemFilter` **没有年份字段**。`apply_to()` 只折叠 tags 和 item_types；
`year:` 和 `author:` 是引擎在检索之后才应用的。把它们当成"恰好为空的过滤器"，
等于把它们直接丢掉。

正确的判据现在有了名字，就放在 `apply_to` 旁边：

```rust
/// Whether `apply_to` carries the whole query.
pub fn is_fully_filterable(&self) -> bool
```

**能表达什么，要由那个类型自己说。** 在调用点手写"文本为空"是在猜它。

### 3.139 没有词的查询就是过滤，过滤是 store 的活

修好判据之后，交叉验证发现 `/items?q=tag:survey` 报的是 **`2+`**——技术上诚实
（`needed = offset+limit+1`），实用上是废话，而正确答案是 28,763。

于是把同一个洞见用到了更要紧的地方：列表接口在解析后若发现查询完全可过滤，
就直接走 store 的分页路径。**精确计数、走索引**：

| 查询 | 之前 | 之后 |
|---|---|---|
| `q=tag:survey` | `2+`，30ms | **28,763，2.3ms** |
| `q=type:journalArticle` | 截断，慢 | **17,650，1.2ms** |
| `q=year:2020` | 0 | 0（仍走排序路径，正确） |
| `q=transformer` | `734+` | `734+`（不变） |

这一串三个改动（§3.137–3.139）没有一个是"想到要优化"才做的，
全是**沿着一个数字对不对一路问下去**问出来的。

### 3.140 编辑一次之后的第一次读，才是真正的交互回路

这几轮把侧栏各项都压到了 2ms——**但那全是热态数字**。量了写后第一次读才发现：
编辑一条文献，下一次侧栏加载要付 collections 31.7ms + 智能计数 84.7ms
（并行下墙钟约 85ms）。缓存按库版本失效，而**编辑会话里每一次改动都让它们全部作废**。

`facets` 是唯一不受影响的（0.7ms），因为 `cache.rs` 早就在"先给旧答案、
背后再算"。把那套策略下沉进 `Versioned<T>`（`look_up` → `Fresh/Stale/Missing`，
外加 `claim`/`release` 防止一拥而上重算同一个东西），两个调用方共用：

| | 写后 | 现在 |
|---|---|---|
| collections | 31.7ms | **0.7ms** |
| 智能收藏夹计数 | 84.7ms | **0.6ms** |

**什么可以给旧值，是由用途决定的，不是由代价决定的。** §3.124 里列表的 total
必须精确——它决定客户端认为有多少页；而架子名字旁边的计数是个标签，晚一拍
没人看得出来，卡 85ms 人人都看得出来。沿用 `cache.rs` 的 20ms 门槛：
小库重算不到一毫秒，用精确性换零收益是笔坏买卖。

### 3.141 "整代清空"把这套策略自己废掉了

改完之后基准红了：`facets first 244.8ms ← COLD`，而我手工 curl 是 0.6ms。
**§3.126 那条守卫抓到了一个真 bug。**

`cache.rs` 的 `CacheState` 每个库只存**一个**版本号，`put` 一旦发现版本变了就
把整张表清空。于是：为**某一个**键写入新版本，会把**其他所有键**的旧答案一并
丢掉——它们下次就从"给旧的"变成"算了再给"。

基准之所以稳定复现，是因为我上轮加的"从 facets 里找最稀有标签"用的是
`?limit=2000`，另一个缓存键。真实用户同样会踩：在"全部文献"和某个收藏夹之间
切一下，就足以把对方的旧答案清掉。

改成**每条记录自带版本号**，容量用 `MAX_ENTRIES` 兜底。

教训有两层。一是**为一个键做的失效，不该波及其他键**。二是这个 bug 已经存在很久，
是**新加的一条基准测量**把它照出来的——而那条测量当初是为了另一件事加的
（§3.123 的"决定的两侧都要有人看着"）。**多量一个角度，常常照出的不是你在找的东西。**

### 3.142 并发是又一个测量角度，而且它照出了重复劳动

按 §3.141（"多量一个角度"）量了首屏的**并发**突发——工作台一次发八个请求。
热态 5.2ms，没问题；**写后 43ms**，而其中 `items?limit=100` 单独测只要 12ms。
不是连接池耗尽（池是 16，只有 8 个请求），是真实的 CPU 竞争，且
**`/items` 和 `/stats` 在同一批里并发计算同一个数**（同一个键、同一个版本，
双双未命中，各算一遍）。

`/stats` 现在整体走 §3.140 的旧值策略——它是状态栏上的标签，不是契约。

**没做的事，以及原因**：结构性答案是"单飞"（同键同版本只算一次，第二个等第一个）。
在这里做不了：`cached_count` 跑在 `db.call` 的阻塞闭包里，等待时会**握着池连接**，
正是 §3.98 那条"查询排队最后表现为别人的 database is locked"。
收益是每次编辑后省十几毫秒，代价是把池耗尽的风险请回来。**记下分析，不做。**

也顺便记住：这个语料上 `/stats` 只要 10ms，低于 20ms 的延迟门槛，所以旧值策略
在这里并不生效——它是为更大的库准备的。**门槛让优化在小库上自动让位于精确性，
这是特性不是失效。**

### 3.143 文档里画了的界面，要真的去数一遍

`docs/06` 的阅读器组件树写着侧栏有「缩略图 | 大纲 | 标注列表 | 搜索」。
实际有标注列表和搜索，**缩略图和大纲一个都没有**——而缩略图端点是我几轮前
刚做的，`Thumbnail` 组件也在，缺的只是一个消费者。

补上了页面缩略图导航栏（`PageRail`）：`IntersectionObserver` 只画进入视野的页，
因为**每一次未命中都是一次完整的 pdf.js 渲染**，急切加载会让三百页的论文在
显示第一页之前先渲染三百页。当前页从阅读器**已经算出来的**那个值取，
而不是再定义一遍"正在读第几页"。
